# 3주 MVP Roadmap

## 운영 기준

실제 일정의 기준은 GitHub Project의 [MVP Roadmap](https://github.com/orgs/sksksksksksss/projects/1/views/8)이다. 이 문서는 날짜를 복사해 관리하지 않고, 왜 그렇게 배치했는지 설명한다.

- 기간: 2026년 8월 3일 월요일 ~ 8월 24일 월요일
- 기능 완료 목표: 8월 21일 금요일
- 출시 확인: 8월 24일 월요일
- 범위: Milestone이 `MVP — 3주 출시`인 P0·P1 Epic, Story와 Task
- 일정 단위: 실제로 완료할 Story와 Task
- 추정치: 순수 구현·검증에 필요한 `Estimate (dev-days)`이며 대기 시간을 포함한 기간과 다를 수 있음
- 담당자: 팀 계정이 합류하기 전에는 Workstream으로 표시하고 가짜 assignee를 넣지 않음

8월 22~23일 주말을 필수 작업일로 가정하지 않는다. 기능은 21일까지 합쳐져야 하며 24일은 배포 상태와 핵심 경로를 다시 확인하는 날이다.

## Workstream

| Workstream | 기본 책임 | 3주 실행 항목 | 추정 합계 |
| --- | --- | --- | --- |
| A 루틴·제품 | 로그인, 안정 루틴, 제품 추천·등록 | #45, #7~#10, #46, #49~#50 | 13 dev-days |
| B 비교·계획 | 루틴 비교, 후보 순서, 계획, 불확실성 | #13~#16 | 6 dev-days |
| C 퀘스트·LAB | 관찰, 리마인드, 진행도, 게임 경험 | #17~#21, #51~#52 | 10 dev-days |
| D Rescue·Archive | 불편 대응, 결과, Archive, 재사용 | #22~#29, #47 | 10 dev-days |
| 공통 기반 | 저장·API·제품 데이터·분석·배포·운영 | #31~#37, #48 | 24 dev-days |

표의 합계는 사용자 흐름 39 dev-days, 공통 기반 24 dev-days다. 이 값은 작업의 상대적인 크기와 분배를 맞추기 위한 추정치이지, 사람별 실제 달력 시간을 대신하지 않는다.

개발자 4명은 PM을 포함한다. 첫 배정 회의에서 A~D 사용자 흐름과 공통 기반 Sub-task를 실제 계정에 나누고, 디자이너 2명은 고정된 개발자 2명씩과 화면을 맞춘다. 사람별 일정은 GitHub Project의 Assignee·시작일·목표일에서 관리한다.

## 주차별 완료 결과

### 1주차 — 기준점과 배포 가능한 얇은 흐름

목표는 기반을 완벽하게 만드는 것이 아니라 실제 URL에서 로그인하고 안정 루틴을 저장하는 가장 얇은 흐름을 만드는 것이다.

- 모노레포, 공통 명령과 초기 배포
- 인증과 사용자 데이터 분리
- 루틴·제품·실험의 핵심 스키마
- MVP 제품·성분·기능 fixture
- 안정 루틴 확정
- 비교·관찰·Rescue Workstream이 사용할 계약 확정

### 2주차 — 한 번의 실험을 끝까지 연결

- 현재 루틴 기반 제품 추천과 후보 저장
- 추가·중복·교체 비교와 실험 계획
- 첫 사용·24시간·중간·종료 퀘스트
- 불편 기록, 변경점 복원과 Rescue 분류
- 최종 결과와 안정 루틴 선택적 갱신
- 기능별 통합을 `main`에서 계속 수행

### 3주차 — 경험 재사용과 P1 완성

- 직접·사진·바코드·구매 이미지 제품 등록
- 반대 근거·불확실성 설명
- Beauty Archive와 다음 추천 재사용
- 개인 반복 관찰·재시험·이력 시각화
- 연구실 기록, 배지, 캐릭터·테마와 브라우저 알림
- 접근성, 오류 복구, 로그·성능·개인정보와 전체 E2E

## 날짜 배치 원칙

1. 같은 A~D Workstream의 Story는 한 개발자가 맡는다는 전제로 겹치지 않게 배치한다.
2. 공통 기반은 PM과 네 개발자가 나눌 수 있으므로 기간이 겹칠 수 있다.
3. 디자인과 개발을 별도 카드로 기계적으로 나누지 않는다. Story 기간 안에서 담당 디자이너와 개발자가 상태와 화면을 맞춘다.
4. P0·P1 Story와 Task는 착수 가능한 결과 단위의 Sub-task를 미리 연결한다. 내부 아키텍처와 코드 구조는 Sub-task에서 고정하지 않는다.
5. Story 목표일은 문서 작성일이 아니라 배포 환경에서 완료 조건을 확인하는 날이다.
6. P1도 MVP 목표다. 일정이 흔들리면 P1의 콘텐츠 양을 줄이되 요구사항을 몰래 제거하지 않는다.

## 의존성 원칙

GitHub의 `Blocked by`에는 **작업을 시작할 수 없는 강한 선행 조건**만 넣는다.

예:

- 인증 Story는 모노레포가 있어야 시작할 수 있다.
- 루틴·비교·관찰·Rescue는 공통 저장·API 계약이 있어야 한다.
- 다음 추천 재사용은 기본 추천과 Archive가 있어야 한다.

사용자 흐름상 앞에 있다는 이유로 모든 Story를 직렬 의존성으로 연결하지 않는다. 네 Workstream은 합의된 계약과 fixture로 병렬 구현하고, Epic 완료 조건에서 실제 연결을 확인한다. 모든 흐름을 `#7 → #8 → #9 → #13 → #15 → #17`처럼 막으면 개발자 4명의 병렬 구조가 사라진다.

## Ready와 일정의 관계

날짜가 있다고 Ready인 것은 아니다. 현재 날짜는 MVP의 계획 창이다. 다음 조건을 만족한 항목만 `Ready`로 이동한다.

- 담당자가 실제 GitHub 계정으로 지정됨
- 연결 요구사항과 기능명세를 확인함
- 강한 선행 이슈가 끝났거나 합의된 계약이 있음
- 구현 결과와 검증 방법이 명확한 Sub-task가 연결됨
- 담당자가 Estimate와 목표일에 동의함

팀 계정이 아직 프로젝트에 없으므로 현재 Story와 Task는 Backlog에 유지한다. 첫 배정 회의에서 Workstream A~D를 개발자에게 매핑하고, 합의된 항목부터 Ready로 옮긴다.

## 일정 변경 규칙

- 담당자가 바뀌면 Workstream보다 Assignee를 먼저 갱신한다.
- Estimate가 커지면 먼저 Story가 사용자 결과 하나인지 다시 확인한다.
- 목표일을 미룰 때는 뒤 이슈와 Epic 완료일 영향을 함께 확인한다.
- Blocked 상태가 되면 원인 이슈를 `Blocked by`로 연결하고 필요한 결정을 본문에 남긴다.
- P0 누락 위험이 있으면 PM이 다른 P1 시작보다 P0 완료를 우선 배정한다.
- Milestone 날짜 변경은 배포 목표 변경이므로 PM만 결정한다.

## Roadmap 완료 기준

- 모든 P0·P1 Story·Task에 Priority, Workstream, 시작일, 목표일과 Estimate가 있다.
- 모든 P0·P1 Story·Task에 구현 결과 중심의 Sub-task가 연결된다.
- 모든 항목이 요구사항과 기능명세에 연결된다.
- 강한 의존성은 GitHub native `Blocked by`로 확인할 수 있다.
- Pn 이슈는 MVP Roadmap 필터에서 제외된다.
- 8월 21일까지 기능 Story를 Integration 또는 Done으로 이동한다.
- 8월 24일 실제 URL의 핵심 E2E와 운영 점검 후 Milestone을 닫는다.
