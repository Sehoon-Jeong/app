# SkinCause 문서

이 폴더는 팀이 제품과 구현 방향을 같은 의미로 이해하기 위한 기준 문서다. 처음 합류한 사람은 아래 순서대로 읽으면 된다.

| 순서 | 문서 | 답하는 질문 |
| --- | --- | --- |
| 1 | [기획 정리](./01-product-brief.md) | SkinCause는 누구의 어떤 문제를 푸는가? |
| 2 | [MVP 정의](./02-mvp-definition.md) | 3주 동안 어디까지 만들고 무엇을 검증하는가? |
| 3 | [기술 스택](./03-technology-stack.md) | 무엇으로 만들며, 왜 그 선택을 했는가? |
| 4 | [요구사항](./04-requirements.md) | MVP에서 반드시 가능해야 하는 것은 무엇인가? |
| 5 | [기능명세](./05-features/README.md) | 사용 흐름과 시스템 동작은 정확히 어떻게 이어지는가? |
| 6 | [데이터 모델](./06-data-model/README.md) | 그 동작과 이력을 어떤 구조로 저장하는가? |
| 7 | [협업 방식](./07-collaboration-guide.md) | 이슈를 어떻게 나누고 누가 어떤 기준으로 끝내는가? |
| 8 | [3주 Roadmap](./08-project-roadmap.md) | 무엇을 언제 병렬로 진행하고 일정은 어떤 기준으로 바꾸는가? |

모든 내용을 한 번에 읽을 필요는 없다. 각 문서의 `한눈에 보기`를 먼저 읽고, 필요한 항목만 내려가서 확인한다.

기능명세와 데이터 모델은 요구사항을 기준으로 작성한다. GitHub 이슈의 제목은 범위를 찾기 위한 지도이며, 상세 요구사항을 대신하지 않는다.

## 문서 관리 원칙

- 제품의 목적과 경계가 바뀌면 기획 문서를 먼저 고친다.
- MVP 포함 여부가 바뀌면 MVP 문서와 GitHub Project의 `Priority`를 함께 고친다.
- 요구사항이 바뀌면 기능명세의 [추적표](./05-features/traceability.md)를 함께 고친다.
- 구현 방식이 바뀌면 기술 문서에 결정 이유와 바꾼 날짜를 남긴다.
- 대화에서 끝난 결정은 결정이 아니다. 다음 작업자가 찾아야 하는 내용은 문서나 이슈에 남긴다.
