# 3주 MVP 협업 방식

## 목표

3주 안에 핵심 흐름을 실제로 사용할 수 있는 URL을 배포한다. 많은 작업을 시작하는 것보다 하나의 사용자 흐름을 끝까지 연결하는 것을 우선한다.

## GitHub에서 일을 관리하는 방법

모든 일은 GitHub Project에서 다음 구조로 관리한다.

> **Priority → Epic → Story/Task → Sub-task**

| 구분 | 의미 |
| --- | --- |
| `Priority` | MVP 포함 시점이다. P0와 P1은 이번 MVP, Pn은 이후 범위다. |
| `Epic` | 여러 기능을 묶는 제품 영역이다. 사람에게 직접 배정하지 않는다. |
| `Story` | 사용자가 시작해서 결과를 얻는 하나의 기능이다. 한 명이 최종 결과를 책임진다. |
| `Task` | 배포나 공통 기반처럼 사용자 기능은 아니지만 독립적으로 끝내야 하는 일이다. 한 명이 최종 결과를 책임진다. |
| `Sub-task` | Story나 Task를 구현·검증 가능한 결과로 나눈 실제 작업·분배 단위다. |

PM이 초기 티켓 구조와 우선순위를 잡는다. P0·P1 Story와 Task는 착수 전에 Sub-task까지 나누고, 담당자와 선행 작업을 정한 뒤 `Ready`로 옮긴다.

Sub-task는 보통 한 사람이 0.5~2일 안에 검증할 수 있는 결과로 만든다. 더 크면 사용자에게 보이는 결과나 검증 경계를 기준으로 나누고, 단지 프론트엔드·백엔드·DB라는 기술 층만으로 쪼개지는 않는다. 부모 담당자가 전체 연결과 완료를 책임하며, 다른 사람이 일부 Sub-task를 맡더라도 부모의 사용자 결과를 함께 확인한다.

Story 제목만 정해진 상태는 기능 목록이다. [통합 기능명세서](./05-features/functional-specification.md)는 기능 간 조건·입력·처리·결과를 비교하는 기준이고, Story 본문은 해당 기능의 상세 사용자 흐름·규칙·예외·완료 조건을 관리한다.

기능명세와 ERD는 처음부터 완성본으로 고정하지 않는다. 개발 착수 전에는 전체 흐름과 핵심 데이터 관계를 기준선으로 합의하고, 각 Story를 `Ready`로 옮길 때 필요한 부분을 구체화한다. 구현 중 달라진 결정은 코드, 통합 기능명세서, Story와 ERD에 같은 PR로 반영한다.

## 한 Story를 끝내는 방법

개발자 4명은 PM을 포함해 모두 풀스택으로 일한다. Story를 맡은 사람은 화면, API, 데이터베이스, 테스트와 배포 후 확인까지 버티컬하게 책임진다.

1. `Ready` Story를 맡고 관련 기획·기능명세·데이터 문서를 읽는다.
2. 디자이너와 정상·빈 상태·오류 흐름을 확인한다.
3. 준비된 Sub-task가 실제 구현 순서와 맞는지 확인하고 필요한 경우 범위만 조정한다.
4. 프론트엔드와 백엔드를 연결해 사용자가 기능을 수행할 수 있게 만든다.
5. 테스트가 통과하면 PR을 `main`에 합치고 배포 환경에서 다시 확인한다.
6. Story 제목의 행동을 실제 URL에서 완료할 수 있을 때 `Done`으로 옮긴다.

코드 작성만 끝났거나 프론트엔드와 백엔드 중 한쪽만 동작하면 완료가 아니다.

Sub-task에는 결과, 관련 화면·데이터·API, 예외와 확인 방법을 적는다. 클래스명, 패키지 구조, 디자인 패턴과 함수 분리처럼 담당자가 결정해야 할 내부 구현은 기획이 고정하지 않는다.

## 역할

- **PM:** 제품·기술·운영의 최종 결정을 맡고, 우선순위·담당자·의존성과 배포를 조율한다.
- **개발자 4명:** 각자 맡은 Story를 버티컬하게 구현하고 결과를 검증한다.
- **디자이너 2명:** 각자 개발자 2명과 고정된 1:2 관계로 협업한다. 공통 UI와 LAB 원칙은 두 디자이너가 함께 맞춘다.

공통 코드에는 별도 주인을 두지 않는다. 인증, 공통 UI와 API 규칙은 누구나 필요한 Story 안에서 수정할 수 있고, 충돌이 생기면 PM이 결정한다.

## AI-native 모노레포

팀원 모두 AI와 함께 티켓을 수행한다. AI가 제품 맥락을 추측하지 않도록 코드, 기획, 요구사항, 기능명세, API 계약과 작업 규칙을 한 저장소에서 관리한다.

- 작업은 GitHub 이슈와 연결된 문서를 읽는 것부터 시작한다.
- 구현 중 계약이 바뀌면 코드와 문서를 같은 PR에서 수정한다.
- AI가 만든 코드와 문서의 검증 책임은 Story 담당자에게 있다.
- 비밀값과 실제 사용자 기록은 승인되지 않은 AI 도구에 입력하지 않는다.

## 일정과 통합

3주 일정은 [MVP Roadmap](https://github.com/orgs/sksksksksksss/projects/1/views/8)과 [일정 원칙](./08-project-roadmap.md)을 기준으로 관리한다. 주 2회 회의에서 완료 결과, 다음 Story, 의존성과 일정 위험을 확인한다.

기능은 마지막 주에 한꺼번에 합치지 않는다. 작동하는 흐름부터 계속 `main`에 통합한다. 동료 리뷰를 필수 승인 절차로 두지는 않지만, PR 작성자는 자동 테스트와 배포 결과에 책임진다.
