# 3주 MVP 협업 방식

## 한눈에 보기

- 팀의 목표는 3주 안에 핵심 흐름이 작동하는 실제 URL을 배포하는 것이다.
- PM이 제품·기술·운영 결정을 맡고, 개발자 4명은 사용자 흐름을 처음부터 끝까지 책임진다.
- 디자이너 2명은 각각 개발자 2명과 고정된 협업 관계를 갖는다.
- GitHub Project는 **Priority → Epic → Story/Task → Sub-task** 구조로 관리한다.
- 완료는 “코드를 작성함”이 아니라 “사용자가 배포 환경에서 흐름을 수행함”을 뜻한다.

## 역할

### PM 겸 프로젝트·테크 리드

- MVP 범위, 우선순위와 담당자를 정한다.
- 사용자 흐름 사이의 의존성과 공통 기술 결정을 조율한다.
- 일정이나 기술 의견이 충돌할 때 최종 결정을 내린다.
- 배포, 운영과 전체 품질을 끝까지 확인한다.

PM이 모든 코드를 직접 통제한다는 뜻은 아니다. 결정이 멈추거나 서로 다른 기준이 생겼을 때 책임지고 하나의 방향을 정한다는 뜻이다.

### 개발자 4명

모두 풀스택 개발자로 일한다. 배정받은 Story의 화면, API, 데이터베이스, 테스트와 버그 수정을 한 사람이 끝까지 책임진다.

프론트엔드 카드와 백엔드 카드를 따로 넘겨받는 방식은 사용하지 않는다. 필요하면 구현 안에서 Sub-task로 나누되, Story의 최종 결과와 통합 책임은 한 명의 오너에게 있다.

### 디자이너 2명

디자이너 한 명이 개발자 두 명과 각각 1:1로 협업한다. 이 관계는 3주 동안 유지한다. 담당 Story의 흐름, 상태와 화면을 함께 완성하고, 두 디자이너가 공통 UI와 LAB 경험 원칙을 조율한다.

디자인은 개발에 넘기고 끝나는 산출물이 아니다. 구현 중 생기는 상태, 문구와 예외를 담당 개발자와 함께 결정한다.

## 일을 나누는 단위

GitHub의 단어는 다음 의미로 사용한다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| `Priority` | MVP 포함 시점 | P0, P1, Pn |
| `Epic` | 여러 사용자 흐름을 묶는 제품 영역 | 안정 루틴과 제품 등록 |
| `Story` | 사용자가 시작해서 결과를 확인하는 하나의 흐름 | 사용자가 아침·저녁 안정 루틴을 저장한다 |
| `Task` | 사용자 흐름은 아니지만 독립적으로 끝내야 하는 작업 | 배포 환경과 CI를 구성한다 |
| `Sub-task` | Story나 Task 안에서 담당자를 나눌 수 있는 작은 작업 | 안정 루틴 입력 화면을 디자인한다 |
| `Bug` | 이미 의도한 동작과 실제 동작의 차이 | 저장 후 제품 순서가 바뀐다 |

### Priority와 Epic은 일이 아니다

P0·P1·Pn은 구현 순서를 나타내는 필드이고, Epic은 관련 기능을 찾기 위한 묶음이다. 개발자에게 “P0를 맡는다”거나 “Epic 전체를 이번 주에 끝낸다”고 배정하지 않는다.

실제 칸반에서 움직이고 사람에게 배정하는 단위는 Story, Task와 Bug다.

### Story는 사용자 결과로 쓴다

좋은 Story는 제목만 보고도 누가 무엇을 할 수 있게 되는지 알 수 있다.

- 좋은 예: `사용자가 새 제품 후보를 비교하고 먼저 시험할 제품을 고른다`
- 피할 예: `추천 시스템 구현`, `API 개발`, `비교 화면`

두 번째 예들은 결과가 아니라 구현 조각이라 제품을 모르는 팀원이 의미를 알기 어렵다.

### Sub-task는 실제 분업이 있을 때만 만든다

Story 오너가 혼자 처리하는 작은 단계까지 모두 이슈로 만들지 않는다. 다음 중 하나에 해당할 때 Sub-task를 만든다.

- 다른 사람이 맡아야 한다.
- 별도의 완료 여부와 의존성을 추적해야 한다.
- 하루 이상 걸리며 Story가 멈춘 이유를 보드에 드러내야 한다.

그 외의 구현 단계는 Story 본문의 체크리스트로 관리한다. Sub-task가 끝나도 Story가 자동으로 사용자에게 가치를 주는 것은 아니므로, 최종 통합과 확인은 Story 오너가 맡는다.

## 권장 담당 영역

실제 이름은 프로젝트 시작 시 넣되, 3주 동안 영역과 협업 관계는 가급적 유지한다.

| 그룹 | 담당 흐름 | 이유 |
| --- | --- | --- |
| 디자이너 A + 개발자 1 | 계정, 안정 루틴과 제품 등록 | 실험의 입력 구조와 첫 사용 경험을 함께 다룬다. |
| 디자이너 A + 개발자 2 | 후보 추천, 루틴 비교와 실험 계획 | 같은 비교 정보가 추천과 계획으로 이어진다. |
| 디자이너 B + 개발자 3 | 관찰 퀘스트, 알림과 LAB 진행 경험 | 사용 시점과 게임 피드백이 하나의 행동 흐름이다. |
| 디자이너 B + 개발자 4 | Rescue, 실험 완료와 Archive | 문제 발생 후 판단이 과거 기록으로 연결된다. |

이 표는 코드 소유권을 뜻하지 않는다. 공통 UI, 인증, API 규칙과 에러 처리는 모두 수정할 수 있다. 다만 공통 변경을 먼저 발견한 사람이 관련 Story 안에서 처리하고, 큰 충돌은 PM이 조율한다.

## 한 Story가 진행되는 방식

1. **PM이 목적을 정리한다.** 사용자, 시작 조건, 기대 결과와 Priority를 확인한다.
2. **디자이너와 개발자가 흐름을 맞춘다.** 정상 상태뿐 아니라 로딩, 빈 상태, 실패와 되돌리기를 확인한다.
3. **Story 오너가 필요한 Sub-task를 만든다.** 실제 분업이나 의존성이 있을 때만 만든다.
4. **세로로 구현한다.** 화면, API, DB와 테스트를 하나의 흐름으로 연결한다.
5. **작게 통합한다.** 오래 분리해 두지 않고 작동하는 단위마다 PR을 `main`에 합친다.
6. **배포 환경에서 확인한다.** 사용자가 처음부터 결과까지 수행되는지 확인한 뒤 Done으로 옮긴다.

## 칸반 상태

| 상태 | 의미 |
| --- | --- |
| Backlog | MVP 후보이지만 아직 바로 시작할 상태가 아니다. |
| Ready | 목적, Priority, 오너와 필요한 선행 작업이 확인됐다. |
| In progress | 오너가 현재 작업 중이다. |
| Blocked | 외부 결정이나 선행 작업 때문에 진행할 수 없다. 이유와 필요한 도움을 적는다. |
| Integration | 코드가 합쳐졌고 배포 환경에서 사용자 흐름을 확인 중이다. |
| Done | 배포 환경에서 완료 기준을 충족했다. |

개발자 한 명은 원칙적으로 `In progress` Story를 하나만 가진다. 새 일을 시작하기보다 현재 흐름을 통합하고 끝내는 것을 먼저 한다. 작은 Bug나 긴급한 공통 Task는 PM이 예외를 정한다.

## 시작 기준과 완료 기준

### Ready로 옮기기 전

- 제목만 보고 사용자 결과 또는 독립 작업 결과를 이해할 수 있다.
- P0, P1, Pn 중 하나가 정해져 있다.
- Epic, 담당자와 선행 작업이 연결되어 있다.
- 디자인이 필요한 상태와 아직 결정하지 않은 질문이 보인다.
- 완료 여부를 확인할 최소한의 인수 조건이 있다.

초기 Story 본문이 아직 비어 있다면 Ready가 아니라 Backlog에 둔다. 이슈를 미리 만들어 구조를 보는 것과 바로 개발할 수 있는 상태는 다르다.

### Done으로 옮기기 전

- 화면, API와 데이터 저장이 배포 환경에서 연결된다.
- 정상·빈 상태·실패 중 해당 흐름에 필요한 상태가 처리된다.
- 합의한 자동 테스트와 `make check`가 통과한다.
- 다른 핵심 흐름을 깨뜨리지 않는다.
- 분석 이벤트, 안전 문구와 접근 권한이 필요한 곳에 반영됐다.
- 사용자가 Story 제목의 행동을 실제로 끝낼 수 있다.

## Git과 PR

- 하나의 모노레포와 짧게 유지하는 기능 브랜치를 사용한다.
- 브랜치 이름은 `story/이슈번호-짧은-설명`, `task/이슈번호-짧은-설명`, `fix/이슈번호-짧은-설명` 형식을 쓴다.
- PR에는 관련 이슈, 사용자에게 바뀐 점, 검증 방법과 화면 변경 이미지를 적는다.
- 동료 승인을 필수 절차로 두지는 않는다. 자동 검사가 통과하면 작성자가 머지할 수 있다.
- 공통 계약, 데이터 삭제, 인증·권한처럼 되돌리기 어려운 변경은 머지 전에 관련 팀원이나 PM에게 알린다.
- 기능을 마지막 주까지 각자 들고 있지 않는다. 작동하는 흐름은 계속 `main`에 합친다.

속도를 위해 리뷰를 생략할 수 있다는 말은 검증을 생략한다는 뜻이 아니다. PR 작성자가 테스트와 배포 결과에 책임진다.

## 회의와 의사결정

정기 회의는 주 2회만 기본으로 둔다.

- **범위·배정 회의:** 완료된 결과를 확인하고 다음 Story의 Priority, 오너와 선행 작업을 정한다.
- **통합·위험 회의:** 흐름 사이의 충돌, 배포 상태와 3주 일정의 위험을 확인한다.

회의 밖에서 막힌 문제는 기다리지 않고 이슈에 남긴 뒤 PM에게 알린다. 다른 도메인에 영향을 주는 결정은 관련 이슈에 한 문단으로 이유를 기록한다. 장기간 유지될 기술 결정은 `docs/`에 반영한다.

## AI 도구 사용

팀원은 익숙한 유료 AI 도구와 작업 방식을 자유롭게 사용한다. 다만 다음 책임은 사람에게 남는다.

- 생성된 코드, 문서와 디자인이 이슈의 목적에 맞는지 확인한다.
- 실행 가능한 테스트로 결과를 검증한다.
- API 계약, 기능 명세와 실제 구현이 달라지면 함께 수정한다.
- 사용자 기록이나 비밀값을 승인되지 않은 도구에 넣지 않는다.
- 이해하지 못한 코드를 그대로 머지하지 않는다.

AI-native 하네스의 의미는 AI가 팀의 규칙을 추측하게 하는 것이 아니다. 저장소 구조, 문서, 계약과 공통 명령을 명확히 만들어 사람과 AI가 같은 기준으로 작업하고 검증하게 하는 것이다.

## 프로젝트가 흔들릴 때의 판단 순서

1. 핵심 사용자 흐름이 실제로 이어지는가?
2. P0가 배포 가능한가?
3. P1의 콘텐츠 양이나 표현 깊이를 줄일 수 있는가?
4. 새 기능 대신 진행 중인 Story를 끝낼 수 있는가?
5. 결정이 다른 흐름에 미치는 영향을 PM이 확인했는가?

3주 프로젝트에서는 더 많은 일을 시작한 팀보다 끝까지 연결한 팀이 이긴다.
