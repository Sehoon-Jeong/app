# 요구사항

각 ID는 사용자가 관찰할 수 있거나 시스템이 검증할 수 있는 한 가지 의무를 나타낸다. 기능 흐름을 설명하는 문서가 아니라, 제품이 반드시 만족해야 하는 결과의 목록이다. `P0`은 핵심 순환에 반드시 필요한 요구사항, `P1`은 핵심을 이해하거나 완결하는 보조 요구사항, `Later`는 이번 구현에서 제외하는 요구사항이다.

## 요구사항 충족 판정

요구사항은 구현됐다는 주장만으로 완료되지 않는다. 다음 네 가지가 모두 있어야 충족으로 본다.

1. 연결된 상세 기능명세에 진입 조건·분기·오류·수용 시나리오가 있다.
2. 외부 계약이 필요한 경우 OpenAPI operation과 오류 코드가 있다.
3. 상태를 저장하는 경우 데이터 모델의 원본 필드·제약이 있다.
4. 정상·권한 위반·AI 실패·빈 상태를 검증하는 테스트가 있다.

UI의 배치·색·문구는 요구사항이 아니다. 반대로 AI가 실패해도 사용자가 기록을 잃지 않는 것, 다른 사용자의 데이터에 접근할 수 없는 것, 정보 부족을 숨기지 않는 것은 화면과 무관하게 지켜야 할 요구사항이다.

## 근거의 종류

`이유` 열은 이미 입증된 사실과 우리가 검증할 제품 가정을 구분해 읽어야 한다. 상세 출처와 가정 ID는 [근거와 가정](./evidence/README.md)에 있다.

| 요구사항 묶음 | 근거 종류 | 현재 근거 또는 가정 | MVP에서 확인할 것 |
| --- | --- | --- | --- |
| 계정·AI 기억 | 제품 가정 | H-05 | 기억 확인·수정·삭제와 추가 질문 감소 |
| 정확한 제품 버전·성분 경계 | 외부 안전 원칙 | EU CosIng, 제조사·공식 정보 우선 | 불확실 버전이 AI 판단에서 실제 제외되는지 |
| 제품 의견·추천 | 제품 가정 | H-01, H-03 | 개인 기록이 연결된 결과의 이해도와 후속 행동 |
| 루틴 순서 | 외부 일반 원칙 + 제품별 사실 | AAD, 제조사 공식 사용법 | 사용자가 AI 제안을 이해하고 적용·수정하는지 |
| 7일 결과 | 제품 가정 | H-02 | 매일 기록 없이도 결과를 회수할 수 있는지 |
| AI Rescue | 외부 안전 경계 + 제품 가정 | FDA, AAD, H-04 | 변경 확인과 다음 루틴이 행동으로 연결되는지 |

7일, 추천 점수 가중치, 조기 결과 가중치는 의학적 사실이 아니라 MVP 운영 규칙이다. 실험 결과에 따라 바꿀 수 있지만 한 실험 안에서는 모든 사용자에게 같은 규칙을 적용한다.

| CAT-06 | P1 | 참고 가격·판매처·확인 시각을 보여줄 수 있지만 제품 의견과 추천 순서에는 쓰지 않는다. | 편의 정보와 판단 근거의 신뢰 수준이 다르다. |
| PRD-01 | P0 | 사용자는 제품명 검색으로 하나의 제품을 내 화장품에 추가한다. | 제품명만 얻으면 최신 카탈로그 정보를 연결할 수 있다. |
| PRD-02 | P0 | 영수증 OCR은 제품명·브랜드·용량 후보만 읽고 사용자가 결과를 확인한다. | OCR이 잘못 읽은 제품을 자동 등록하지 않는다. |
| PRD-03 | P0 | 영수증으로 등록된 모든 제품은 미사용 상태로 시작하며 현재 루틴에 자동 추가하지 않는다. | 구매와 실제 사용은 다른 사건이다. |
| PRD-04 | P1 | 제품별 짧은 메모를 저장하고, 사용자가 요청한 AI 분석에 맥락으로 쓴다. | 사용 이유나 특이사항 같은 비정형 맥락을 잃지 않는다. |
| PRD-05 | P0 | 내 화장품은 미사용 화장품, 현재 루틴, 마지막 안정 루틴으로 나누어 보여준다. | 사용 상태를 세밀하게 나열하는 것보다 다음 행동을 이해하기 쉽다. |
| PRD-06 | P0 | 사용자는 제품을 내 화장품에서 삭제한다. 사용량·소진·유통기한은 추적하지 않는다. | MVP에는 재고 관리보다 경험 연결이 중요하다. |

## 3. 제품 의견과 추천

| ID | 우선순위 | 요구사항 | 이유 |
| --- | --- | --- | --- |
| OPN-01 | P0 | 사용자는 외부에서 본 한 제품을 검색해 “이거 사볼까?” 의견을 요청한다. | 이미 가진 후보 중 고르는 기능이 아니라 구매 직전 질문이다. |
| OPN-02 | P0 | 의견은 사용자의 현재 목적, 현재·안정 루틴, 가진 제품, 과거 사용 기록, 제품 메모와 확인된 외부 근거를 함께 사용한다. | 일반 제품 설명과 개인화된 구매 의견을 구분한다. |
| OPN-03 | P0 | 결과는 `지금 고려할 이유가 큼`, `비슷한 제품이 이미 있음`, `현재 목적과 거리가 있음`, `판단할 정보가 부족함` 중 하나와 지지·반대·불확실 근거를 보여준다. | 좋다/나쁘다 대신 구매 맥락의 결론을 명확히 한다. |
| OPN-04 | P0 | 사용자는 결과 화면에서 제품에 관해 후속 질문하고, AI는 현재 분석과 출처를 이어서 사용한다. | 정적인 카드만으로는 사용자의 실제 궁금증을 다루기 어렵다. |
| OPN-05 | P1 | 비슷한 제품은 최대 5개를 보여주며 이미 가진 제품은 `보유 중`으로 표시하고 선택을 막는다. | 중복 구매를 피하고 비교 범위를 제한한다. |
| OPN-06 | P1 | 사용자는 제품을 찜하거나 샀다고 표시해 내 화장품에 넣는다. | 구매 전 판단을 이후 사용 기록과 연결한다. |
| REC-01 | P0 | 사용자는 원하는 변화를 자연어로 말하고 필요할 때 AI의 추가 질문에 답한다. | 미리 만든 피부 상태 enum에 사용자를 억지로 맞추지 않는다. |
| REC-02 | P0 | AI는 한국 제품 카탈로그와 허용된 외부 출처를 검색해 0~5개 후보를 제안하고 서버가 실제 제품 버전·출처·중복·금지 조건을 검증한다. | AI의 탐색 능력을 쓰되 존재하지 않는 제품과 근거를 차단한다. |
| REC-03 | P0 | 후보 수를 채우기 위해 약한 제품을 넣지 않으며 각 후보에 추천 이유, 망설일 이유, 정보 부족과 관찰할 점을 표시한다. | 추천 수보다 설명 가능한 근거가 중요하다. |
| REC-04 | P0 | 추천은 적합 확률, 효능 보장, 안전 판정이나 인기 순위가 아니다. | 서비스의 역할을 의료·광고 판단과 구분한다. |

| RTN-06 | P0 | 사용자가 AI 적용을 누르면 제안된 순서·빈도를 편집안에 반영한다. 모호하거나 상충하는 정보는 먼저 사용자에게 묻는다. | AI가 임의로 실제 사용을 정하지 않는다. |
| RTN-07 | P0 | 루틴 저장 직후 AI 분석을 비동기로 실행한다. 실패해도 루틴은 저장되고 화면 상단에서 재시도할 수 있다. | 저장과 외부 AI 장애를 분리한다. |
| RTN-08 | P0 | 각 루틴 제품에 그 위치·역할·확인할 점과 근거를 AI 설명으로 제공한다. | 루틴 전체가 아니라 각 제품이 왜 그 자리에 있는지 알게 한다. |

| OBS-02 | P0 | 7일 결과는 먼저 기록된 제품·순서·빈도와 실제 사용이 대체로 같았는지 묻는다. | 기록과 실제 조건이 다르면 결과를 그 루틴에 붙일 수 없다. |
| OBS-03 | P0 | 실제 사용이 같으면 `불편 없음`, `불편함`, `더 써봐야 함` 중 하나를 받는다. | 안정 승급, Rescue, 관찰 연장의 분기를 만든다. |
| OBS-04 | P0 | 불편 없음이면 해당 버전을 마지막 안정 루틴으로 승급한다. | 다음 비교와 Rescue의 기준점을 만든다. |
| OBS-05 | P0 | 불편함이면 같은 대화 안에서 Rescue를 시작한다. | 사용자가 같은 내용을 다시 입력하지 않게 한다. |
| OBS-06 | P0 | 더 써봐야 함이면 같은 루틴을 7일 더 사용한 뒤 다시 묻되 최대 두 번까지만 자동 연장한다. | 사용 횟수가 부족한 경우를 억지로 판정하지 않으면서 반복 알림이 끝없이 이어지지 않게 한다. |
| OBS-07 | P0 | 실제 사용이 달랐으면 결과를 안정 루틴에 쓰지 않고 루틴을 고친 뒤 새 7일을 시작한다. | 잘못된 조건의 데이터를 강한 개인 근거로 만들지 않는다. |
| OBS-08 | P0 | 7일 전에 루틴을 바꾸려 하면 지금까지의 전반적 결과를 선택적으로 묻고 낮은 신뢰도로 저장한다. 답하지 않아도 편집을 계속한다. | 짧은 경험도 보존하되 안정으로 보지 않는다. |

## 5. AI Rescue

| RSC-03 | P0 | AI는 증상 표현, 발생 시점, 실제 사용, 최근 다른 변화와 현재 심한 정도 중 필요한 정보만 추가 질문한다. | 장문의 설문 없이 분석에 필요한 빈틈만 채운다. |
| RSC-04 | P0 | 서버는 마지막 안정 루틴 이후의 제품·순서·빈도 변경을 계산하고 사용자가 사실을 수정한다. | 기억이 아니라 저장된 변경을 분석의 출발점으로 삼는다. |
| RSC-05 | P0 | AI는 제품 공식 정보, 완제품 인체 연구와 관련 원료 연구, 사용 시점, 함께 바뀐 항목, 과거 개인 기록을 검색하고 서버 규칙이 확인 순위를 계산한다. | 단순한 성분 블랙리스트보다 현재 맥락을 반영하면서 AI가 순서를 임의로 바꾸지 못하게 한다. |
| RSC-06 | P0 | 각 순위에는 지지 근거, 반대 근거, 정보 부족과 출처를 함께 보여주며 원인 확률로 표현하지 않는다. | 순위가 진단이나 범인 확정처럼 보이지 않게 한다. |
| RSC-07 | P0 | AI는 사용자가 선택할 보수적인 다음 루틴 하나를 제품·순서·빈도로 제안한다. | 분석만 하고 끝내지 않고 다음 행동까지 연결한다. |
| RSC-08 | P0 | 사용자가 제안을 적용하면 독립된 새 현재 루틴 버전과 새 7일이 시작된다. `복구 중` 같은 별도 상태는 두지 않는다. | Rescue 이후에도 같은 루틴 학습 순환을 사용한다. |
| RSC-09 | P0 | 사용자가 기록만 남기면 현재 7일은 계속되고 홈에 `Rescue 기록 있음 · 루틴 변경 없음`을 표시한다. | 사용자의 실제 행동을 임의로 바꾸지 않는다. |
| RSC-10 | P0 | 새 루틴에서도 불편하면 그 버전을 기준으로 새 Rescue를 시작하고 과거 Rescue는 참고 근거로 사용한다. | 반복되는 상황에서도 각 루틴의 조건을 독립적으로 보존한다. |
| RSC-11 | P0 | 안정 루틴이 없으면 가장 오래 문제없이 기록된 제품과 개인 맥락으로 최소 루틴을 제안하되 기준점이 약함을 명시한다. | 도움이 필요한 순간에 단순히 중단 안내만 하지 않는다. |
| RSC-12 | P0 | 루틴 자체가 없으면 일반 안전 안내와 자유 기록은 제공하지만 제품별 확인 순위는 만들지 않는다. | 비교할 사용 사실이 없을 때 거짓 정밀도를 만들지 않는다. |
| RSC-13 | P0 | 사용자가 심각하거나 빠르게 악화된다고 말하면 제품 분석을 이어가지 않고 전문가 확인을 제안한다. 구체적 진단·응급도·진료과는 정하지 않는다. | 서비스가 다룰 수 없는 의료 판단의 경계를 지킨다. |

## 6. 이력과 알림

| ID | 우선순위 | 요구사항 | 이유 |
| --- | --- | --- | --- |
| HIS-01 | P0 | 사용자는 현재 루틴과 과거 버전을 시간순으로 보고 제품·순서·빈도·결과·생성 이유를 확인한다. | 개인 데이터가 쌓였다는 가치를 눈으로 확인한다. |
| HIS-02 | P0 | 두 루틴 버전의 추가·삭제·순서·빈도 차이를 비교한다. | Rescue와 다음 구매 의견의 근거를 이해한다. |
| HIS-03 | P1 | 제품 상세에서 해당 제품이 포함된 루틴 기록과 결과로 이동한다. | 제품과 루틴 경험을 연결한다. |
| NOT-01 | P0 | 알림은 앱 안에서만 제공하며 7일 결과와 비동기 AI 작업 완료를 알린다. | 해커톤 범위에서 채널을 단순화한다. |
| NOT-02 | P0 | 알림을 열거나 읽는 행위 자체를 사용 결과로 해석하지 않는다. | 응답하지 않은 사용자를 문제없음으로 오해하지 않는다. |

## 7. AI, 보안과 운영

| ID | 우선순위 | 요구사항 | 이유 |

| AI-02 | P0 | 서버는 사용자 권한, 실제 제품 ID·버전, 현재 루틴, 상태 전이, 저장 가능 필드와 AI 출력 스키마를 검증한다. | AI가 시스템 사실을 만들거나 다른 사용자의 데이터를 바꾸지 못하게 한다. |
| AI-03 | P0 | AI 결과는 주장마다 출처 또는 개인 기록 참조를 가지며 관찰, 해석, 불확실성을 구분한다. | 출처 링크만 붙인 그럴듯한 설명을 막는다. |

| AI-05 | P0 | 영수증 OCR, 추천, 제품·성분 조사와 Rescue 분석은 비동기 작업으로 상태와 재시도를 저장한다. | 긴 요청과 중복 실행을 안전하게 다룬다. |
| SEC-01 | P0 | 모든 개인 리소스에서 인증 사용자의 소유권을 검사한다. | 개인 기록 유출을 막는다. |
| SEC-02 | P0 | 비밀값과 실제 사용자 데이터를 저장소, 로그, 프롬프트 예제와 테스트 fixture에 넣지 않는다. | 개발 과정의 유출을 막는다. |

| OPS-03 | P0 | 한 번만 일어나야 하는 쓰기는 멱등 키를 받고 비동기 작업은 동일 입력 해시로 중복을 막는다. | 재시도와 더블 탭으로 중복 루틴·결과가 생기지 않게 한다. |
