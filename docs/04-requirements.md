# 요구사항

각 ID는 사용자가 관찰할 수 있거나 시스템이 검증할 수 있는 한 가지 의무다. 이 문서는 **P0 → P1 → P2 순서**로 읽고 구현한다. 같은 기능에 P0와 이후 범위가 함께 있어도 P0 계약이 먼저다.

## 우선순위 기준

| 우선순위 | 의미 | 착수 조건 |
| --- | --- | --- |
| `P0` | SkinCause의 핵심 학습 순환을 한 번 끝내고 공개 사용자의 기록을 안전하게 지키는 데 필수 | 지금 구현 |
| `P1` | P0의 이해도·회수율·운영 안정성을 높이지만 핵심 가설 자체에는 필수가 아님 | P0 E2E와 핵심 지표 수집 후 |
| `P2` | 입력 편의, 탐색 확장 또는 별도 가치 제안 | P0·P1 지표로 필요가 확인된 뒤 |

우선순위는 중요도의 감상이 아니라 의존 순서다. P1·P2 API와 데이터 구조를 미리 고려할 수는 있지만 P0 완료 전에 해당 화면과 작업을 구현하지 않는다.

## P0가 검증하는 한 가지 순환

```text
최소 제품 의견
  → 내 화장품 등록
  → 현재 루틴 버전 저장
  → 7일 결과와 안정 루틴
  → 불편하면 AI Rescue
  → 사용자가 다음 루틴 적용
  → 이 경험을 다음 제품 의견에 재사용
```

제품을 처음부터 찾아주는 추천은 P2다. 그러나 외부에서 본 한 제품을 현재 루틴과 과거 결과로 설명하는 최소 `이거 사볼까?`는 이전 경험이 다음 판단에 재사용되는지를 확인하므로 P0다.

## 요구사항 충족 판정

요구사항은 다음 네 가지가 모두 있어야 충족한다.

1. 상세 기능명세에 진입 조건·분기·오류·수용 시나리오가 있다.
2. 외부 계약이 필요하면 OpenAPI operation과 오류 코드가 있다.
3. 상태를 저장하면 데이터 모델의 원본 필드·제약이 있다.
4. 정상·권한 위반·AI 실패·빈 상태를 검증하는 테스트가 있다.

UI 배치·색·문구는 요구사항이 아니다. AI 실패 후 기록 보존, 교차 사용자 접근 차단과 불확실성 표시는 UI와 무관하게 지킨다.

## P0 · 핵심 학습 순환

### 계정과 안전한 데이터 경계

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| ACC-01 | 공개 MVP 사용자는 이메일로 가입·로그인하고 자기 데이터에만 접근한다. 클릭 프로토타입은 고정 테스트 계정으로 대체할 수 있다. | 개인 경험이 다른 사용자와 섞이면 모든 판단이 무효다. |
| ACC-02 | 사용자는 계정과 연결 기록의 영구 삭제를 요청할 수 있다. | 실제 사용자의 개인 기록을 받는 순간 필요한 통제다. |
| SEC-01 | 모든 개인 리소스에서 인증 사용자의 소유권을 검사하고 개인 자식 데이터의 복합 FK가 같은 사용자 부모만 참조하게 한다. | API 누락이나 내부 버그로도 교차 사용자 연결을 저장하지 않는다. |
| SEC-02 | 비밀값과 실제 사용자 데이터를 저장소, 로그, 프롬프트 예제와 테스트 fixture에 넣지 않는다. | 개발 과정의 유출을 막는다. |

### 최소 제품 등록과 구매 의견

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| PRD-01 | 사용자는 큐레이션된 제품을 제품명으로 찾거나 이름을 직접 입력해 내 화장품에 추가한다. 등록만으로 현재 루틴은 바뀌지 않는다. | 제품 등록 편의보다 실제 제품과 사용 기록 연결이 먼저다. |
| CAT-03 | 정확한 버전을 확인하지 못한 제품도 이름과 사용 사실은 기록할 수 있지만 성분·기능·사용법을 AI 사실 근거로 사용하지 않는다. | 입력을 막지 않으면서 모르는 제품 사실을 만들지 않는다. |
| OPN-01 | 사용자는 외부에서 본 한 제품을 골라 `이거 사볼까?` 의견을 요청한다. | 핵심 순환의 대표 진입점이다. |
| OPN-02 | 최소 제품 의견은 현재 목적, 현재·안정 루틴과 과거 루틴 결과를 사용한다. P0에서 없는 외부 제품 사실은 `정보 부족`으로 남긴다. | 일반 AI 설명과 개인 기록 재사용을 구분한다. |
| OPN-03 | 결과는 고려할 이유, 겹치는 이유, 현재 목적과의 거리 또는 정보 부족 중 하나와 근거·반대·불확실성을 보여준다. 적합·안전·효능을 보장하지 않는다. | 좋다/나쁘다 판정 없이 행동 가능한 결론을 준다. |
| OPN-06 | 사용자가 `샀어요`를 선택하면 정확한 제품 또는 입력 이름을 내 화장품에 추가하고 루틴에는 자동 반영하지 않는다. | 구매 전 판단을 이후 사용 기록에 연결한다. |

### 루틴 버전과 7일 결과

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| RTN-01 | 루틴은 제품, 아침/저녁, 바르는 순서와 실제 빈도를 가진 불변 버전이다. 한 버전은 한 번의 실제 사용기간이며 클렌징도 포함한다. | Rescue가 당시 조건을 복원하려면 덮어쓸 수 없다. |
| RTN-02 | 제품 하나로도 루틴을 시작할 수 있고 빈도 입력을 건너뛰면 `매일` 기본값을 사용자가 확인한다. | 진입은 단순하게 유지하되 비교 가능한 빈도를 남긴다. |
| RTN-03 | 제품·순서·시간대·빈도 변경을 저장하면 기존 루틴을 보존하고 새 ACTIVE 버전과 새 7일 schedule을 만든다. 과거 버전을 다시 활성화하지 않는다. | 변경 전후와 실제 사용기간을 분리한다. |
| RTN-04 | 사용자는 내 화장품을 추가·제거하고 아침/저녁, 순서와 빈도를 직접 편집한다. 목록에 없는 제품은 등록 후 같은 편집안으로 돌아온다. | AI 순서 추천 없이도 핵심 루틴 사실을 기록한다. |
| OBS-01 | 루틴 시작 현지 날짜를 DAY 1로 하고 DAY 7 00:00부터 앱 안에서 결과 행동을 노출한다. 미응답을 어떤 결과로도 추정하지 않는다. | 문제없었던 경험은 사용자가 돌아오지 않으면 수집되지 않는다. |
| OBS-02 | 결과를 남길 때 기록된 제품·순서·빈도와 실제 사용이 대체로 같았는지 먼저 묻는다. | 다른 조건의 결과를 해당 루틴 근거로 붙이지 않는다. |
| OBS-03 | 실제 사용 일치, 관찰 결과와 다음 행동을 분리해 저장한다. `불편 없음`, `불편함`, `아직 모르겠음`을 각각 완료, Rescue 시작, 결론 보류로 저장한다. P0는 결론 보류 뒤 새 일정을 자동 생성하지 않는다. | 관찰과 시스템 행동을 같은 enum에 섞지 않고 자동 연장은 P1로 남긴다. |
| OBS-04 | 실제 사용이 같고 불편 없음으로 완료한 현재 루틴만 마지막 안정 루틴으로 승격하고 과거 안정 이력을 보존한다. | 다음 비교와 Rescue의 기준점을 만든다. |
| OBS-05 | 불편함을 선택하면 이전 결과 대화를 지우지 않고 Rescue로 이어간다. | 같은 사실을 다시 입력시키지 않는다. |
| OBS-07 | 실제 사용이 기록과 다르면 안정 루틴으로 쓰지 않고 실제 사용대로 새 루틴을 저장하게 한다. | 잘못된 조건을 강한 개인 근거로 만들지 않는다. |

### AI Rescue와 다음 루틴

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| RSC-01 | 사용자는 7일 전후와 관계없이 자유 문장으로 불편함을 말해 Rescue를 시작한다. | 불편이 생긴 순간이 핵심 진입점이다. |
| RSC-02 | Rescue는 이전 사용자·AI 메시지를 지우지 않고 아래로 이어지는 채팅이며 빠른 답만 선택 버튼을 함께 제공한다. | 사용자가 판단 과정을 따라가고 정정할 수 있어야 한다. |
| RSC-03 | AI는 발생 시점, 실제 사용, 함께 바뀐 것과 사용자가 말한 심한 정도 중 판단에 필요한 빈칸만 한 번에 하나씩 묻는다. 모르면 건너뛸 수 있다. | 장문의 진단 설문과 억지 추정을 막는다. |
| RSC-04 | 서버는 마지막 안정 루틴과 현재 루틴의 제품·순서·시간대·빈도 차이를 계산하고 사용자가 실제와 다른 변경을 고친다. | AI 기억이 아니라 저장된 변경을 출발점으로 삼는다. |
| RSC-05 | P0 확인 우선순위는 새로 추가·제거된 제품, 시간대·순서·빈도 변화, 함께 바뀐 항목, 발생 시점과 관련 과거 기록으로 계산한다. 큐레이션된 공식 사실은 있을 때만 보조 근거로 쓴다. | 먼저 변경점 정리 엔진의 가치를 검증하고 외부 연구 엔진과 섞지 않는다. |
| RSC-06 | 각 확인 순위는 먼저 보는 이유, 반대 개인 기록과 정보 부족을 함께 보여주며 원인·범인·확률로 표현하지 않는다. | 행동 순서를 진단처럼 오해하지 않게 한다. |
| RSC-07 | AI는 보유 제품 안에서 유지·제외·순서·빈도가 명확한 보수적 다음 루틴 하나를 제안한다. 새 제품을 추가해 해결하지 않는다. | 분석을 실제 다음 행동으로 연결한다. |
| RSC-08 | 사용자가 정확한 plan을 승인한 뒤에만 독립된 새 루틴 버전을 만들고 새 7일을 시작한다. 적용 직전 plan의 기준 루틴과 현재 ACTIVE를 비교한다. | 오래된 AI 결과가 최신 루틴을 덮어쓰지 않게 한다. |
| RSC-12 | 현재 루틴이 없으면 일반 안전 안내와 자유 기록만 제공하고 제품별 확인 순위와 개인화 루틴을 만들지 않는다. | 비교 사실이 없을 때 거짓 정밀도를 만들지 않는다. |
| RSC-13 | 사용자가 심각하거나 빠르게 악화된다고 말하면 제품 순위와 루틴 제안을 중단하고 전문가 확인을 권한다. 질환·응급도·진료과는 정하지 않는다. | 서비스가 할 수 없는 의료 판단의 경계를 지킨다. |
| HIS-02 | 사용자는 현재 루틴과 마지막 안정 루틴의 제품·순서·시간대·빈도 차이를 본다. | Rescue가 무엇을 기준으로 판단했는지 확인한다. |

| AI-04 | AI가 실패해도 사용자가 저장한 제품·루틴·결과·대화는 남고 고정 안내, 직접 편집과 재시도 경로를 제공한다. | 외부 장애가 핵심 기록을 잃게 하지 않는다. |

| OPS-02 | AI와 Object Storage 호출은 DB 쓰기 트랜잭션 밖에서 실행한다. | 외부 지연으로 SQLite 쓰기 잠금을 오래 잡지 않는다. |
| OPS-03 | 한 번만 반영할 쓰기는 멱등 키를 사용하고 AI plan 적용 전 기준 루틴과 ACTIVE 루틴을 비교한다. | 더블 탭·재시도·오래된 제안으로 중복 상태를 만들지 않는다. |

## P1 · 핵심 순환 강화

P1은 P0 E2E가 동작하고 사용자가 실제로 Rescue 제안을 이해·적용한다는 증거가 나온 뒤 착수한다.

### 제품·루틴 설명 강화

| ID | 요구사항 | 이유 |
| --- | --- | --- |
| CAT-01 | 국내 판매 스킨케어·클렌징·선케어의 실제 출시판을 카탈로그로 관리한다. | 테스트 제품을 넘어 실제 사용자 제품을 안정적으로 연결한다. |
| CAT-02 | 제품은 브랜드, 이름, 처방·용량·포장·시장 단서가 같은 출시판으로 식별한다. | 서로 다른 버전의 공식 정보가 섞이지 않게 한다. |
| CAT-04 | 제품 사실은 적용 출시판과 확인 당시 evidence snapshot을 참조한다. | 나중에 같은 설명을 재검증한다. |
| CAT-05 | 제조사·브랜드, 정부·규제기관, 공식 DB·원 논문만 근거로 사용하고 리뷰·커뮤니티는 제외한다. | 인기와 제품 사실을 분리한다. |
| PRD-04 | 사용자는 제품별 짧은 메모를 남기고 명시적으로 허용한 AI 요청에만 포함한다. | 비정형 사용 맥락을 통제 가능하게 보존한다. |
| PRD-05 | 내 화장품을 미사용, 현재 루틴, 마지막 안정 루틴 관계로 묶어 보여준다. | 저장 제품이 어떤 맥락에 있는지 이해한다. |
| PRD-06 | 사용자는 현재 루틴 연결을 먼저 정리한 뒤 내 화장품을 삭제한다. 과거 루틴 참조는 보존한다. | 현재 상태와 과거 기록을 함께 지킨다. |
| OPN-04 | 사용자는 제품 의견에서 후속 질문하고 AI는 같은 입력 snapshot과 검증된 근거를 이어서 사용한다. | 정적 결과 뒤 실제 궁금증을 해결한다. |

| RTN-08 | 각 제품의 현재 위치·확인된 역할·정보 부족과 근거를 표시한다. | 루틴 전체뿐 아니라 제품별 맥락을 이해한다. |

## 근거의 종류

상세 출처와 가정 ID는 [근거와 가정](./evidence/README.md)에 있다.

| 요구사항 묶음 | 근거 또는 가정 | 확인할 것 |
| --- | --- | --- |
| 최소 제품 의견 | H-01, H-03 | 개인 루틴·결과를 쓴 의견이 일반 설명보다 유용한가 |
| 루틴·7일 결과 | H-02 | 매일 기록 없이도 문제없음 결과를 회수할 수 있는가 |
| AI Rescue | FDA·AAD 안전 경계, H-04 | 변경 확인과 다음 루틴이 실제 행동으로 이어지는가 |
| AI 기억 | H-05 | P0 구조화 이력만으로 부족한 개인 맥락이 확인되는가 |

7일과 확인 순위 규칙은 의학적 기준이 아니라 모든 P0 사용자에게 동일하게 적용하는 제품 운영 규칙이다.

## 이번 제품에서 하지 않는 것

- 피부 질환·알레르기·원인·응급도·진료과 진단
- 제품 적합 확률과 효능·안전 보장
- 메이크업·헤어·향수 카탈로그
- 잔량·소진일·유통기한 관리
- 가격·판매량·광고비를 이용한 판단 순위
- 푸시·문자·이메일 알림
- 매일 피부 일기와 출석·퀘스트·LAB 게임화
- 과거 루틴과 AI run의 사후 수정
