# 협업과 구현 흐름

## 목적

기능별로 따로 개발한 뒤 마지막에 연결하지 않는다. 먼저 제품 전체가 한 번 동작하는 통합 초안을 만들고, 이후 각 영역을 맡은 개발자가 같은 기준으로 운영 가능한 수준까지 완성한다.

이 방식의 목표는 두 가지다.

- 제품의 핵심 순환이 초반부터 끝까지 연결되어 있는지 확인한다.
- 병렬 개발 중에도 기획, 디자인, API와 구현이 서로 다른 방향으로 가지 않게 한다.

## 시작 조건

구현을 시작할 때 다음 자료가 준비되어 있어야 한다.

1. GitHub Feature 기능명세와 연결된 Task
2. 기능별 요구사항과 수용 조건
3. OpenAPI 계약과 데이터 모델
4. 사용자가 실제로 누를 수 있는 프로토타입

자료가 서로 충돌하면 구현으로 덮지 않는다. Feature 이슈에서 결정한 뒤 요구사항, OpenAPI, 데이터 모델과 프로토타입을 함께 고친다.

## 역할

| 역할 | 책임 |
| --- | --- |
| 기획 책임자 | 제품 결정, 우선순위와 수용 조건을 확정한다. |
| 통합 구현 담당자 1명 | AI를 활용해 전체 P0 흐름의 통합 초안을 만든다. 기능 사이의 연결과 계약 누락을 먼저 찾는다. |
| 영역 책임 개발자 4명 | 맡은 기능을 API, 데이터, 예외, 테스트까지 포함해 운영 가능한 수준으로 완성한다. |
| 디자이너 2명 | 사용자 스토리별 인터페이스와 상태를 설계하고 Figma 원본을 관리한다. |
| AI | 구현, 테스트 작성과 프로토타입 갱신을 돕는다. 제품 결정과 최종 검수의 주체가 되지 않는다. |

## 전체 흐름

### 1. 구현 기준을 고정한다

작업을 시작하기 전에 담당 Feature, 요구사항 ID, API와 데이터 계약, 프로토타입 화면을 연결한다. 제품 결정이 남아 있거나 선행 작업이 끝나지 않은 Task는 `Ready`로 올리지 않는다.

### 2. 한 사람이 전체 통합 초안을 만든다

통합 구현 담당자는 AI와 함께 P0 기능을 처음부터 끝까지 한 번 연결한다.

```text
제품 탐색
→ 실제 사용 맥락 저장
→ 경험 원문 기록
→ 개인 패턴과 근거 연결
→ 다음 제품 탐색에 재사용
→ 불편 경험은 같은 AI 채팅의 Rescue로 연결
```

이 단계의 결과는 최종 구현이 아니다. 다음을 빠르게 확인하는 실행 가능한 기준점이다.

- 기능 사이의 입력과 출력이 실제로 연결되는가
- OpenAPI와 데이터 모델만으로 흐름을 구현할 수 있는가
- 기획에 빠진 상태와 예외가 무엇인가
- 프로토타입과 명세가 서로 다르게 해석되는 부분이 있는가

거대한 한 번의 PR로 합치지 않는다. 제품 탐색, 사용 맥락, 경험 기록, 패턴, Rescue처럼 검토 가능한 수직 흐름 단위로 나누어 병합한다. 각 PR은 최소 실행과 계약 테스트를 통과해야 한다.

### 3. 네 명의 개발자가 기능 영역을 책임진다

통합 초안이 연결되면 네 명의 개발자가 Feature 영역을 나눠 맡는다. 초안 코드를 그대로 인정하지 않고 담당 영역의 모든 정상·실패 경로를 다시 검토한다.

영역 책임자는 다음을 함께 맡는다.

- Feature의 사용자 흐름과 모든 분기
- 프론트엔드와 API 연결
- 데이터 저장과 migration
- 권한, 소유권과 상태 전이
- 빈 상태, AI 실패, 재시도와 중복 요청
- 단위·통합·E2E 테스트
- 관련 OpenAPI와 데이터 문서 갱신

프론트엔드, 백엔드처럼 계층만 나눠 소유하지 않는다. 한 기능의 결과가 실제 사용자에게 도달할 때까지 한 사람이 책임진다. 공통 기반을 바꿀 때는 영향을 받는 영역 책임자와 함께 검토한다.

### 4. 디자인은 병렬로 진행한다

디자이너 두 명은 개발과 병렬로 사용자 스토리별 인터페이스를 설계한다. Figma에는 정상 화면만이 아니라 최소한 다음 상태가 포함되어야 한다.

- 최초 진입과 빈 상태
- 입력 중과 제출 중
- 성공 결과
- 정보 부족과 `잘 모르겠어요`
- 오류와 재시도
- AI 응답 대기와 실패
- 사용자가 취소하거나 이전으로 돌아가는 상태

Feature가 사용자 행동과 분기를 정의하고, Figma는 화면 구조와 시각적 상호작용을 정의한다. 디자이너가 제품 동작을 바꾸고 싶다면 Figma에만 반영하지 않고 Feature 이슈에서 먼저 결정한다.

### 5. 테스트 하네스 화면을 Figma 디자인으로 교체한다

통합 초안의 화면은 기능 연결을 확인하는 테스트 하네스 수준으로 시작해도 된다. 하나의 사용자 스토리 디자인이 끝날 때마다 해당 영역의 실제 제품 화면을 Figma 기준으로 갱신한다.

1. 디자이너가 Figma 링크와 대상 프레임, 상태 목록을 Feature 이슈에 연결한다.
2. 기획 책임자가 기존 흐름과 달라진 제품 결정을 확인한다.
3. 영역 책임 개발자가 AI의 도움을 받아 통합 초안의 실제 화면을 Figma 디자인과 상태로 교체한다.
4. HTML 프로토타입을 수동 인수 테스트에 계속 사용한다면 같은 스토리의 핵심 상태도 함께 맞춘다.
5. 디자이너가 레이아웃과 상호작용을, 영역 책임 개발자가 실제 데이터·상태·접근성을 검수한다.
6. 승인된 실제 화면과 프로토타입으로 해당 스토리의 인수 테스트를 수행한다.

AI가 Figma를 코드로 옮긴 결과는 초안이다. 디자이너 확인 없이 시각 기준으로 확정하지 않는다. 디자인 반영 과정에서 새로운 분기나 데이터가 필요해지면 코드에만 추가하지 않고 Feature와 계약을 먼저 수정한다.

### 6. 영역별 완료 결과를 다시 하나로 검증한다

각 영역이 끝나면 P0 경험 순환 전체를 다시 실행한다. 개별 기능 테스트 통과만으로 완료하지 않는다.

- 이전 단계에서 만든 데이터가 다음 단계에서 실제 근거로 사용되는가
- AI가 실패해도 제품, 루틴과 사용자 입력이 보존되는가
- 다른 사용자의 데이터에 접근할 수 없는가
- AI 요약이 원문을 덮거나 정보 부족·미응답이 긍정 결과로 바뀌지 않는가
- Figma, 프로토타입과 실제 제품의 핵심 분기가 같은가

## 문제를 발견했을 때

| 발견한 문제 | 처리 방법 |
| --- | --- |
| 명세대로 만들었지만 사용 흐름이 어색함 | Feature 이슈에 문제와 선택지를 남기고 제품 결정을 받는다. |
| 필요한 분기나 상태가 명세에 없음 | Feature와 요구사항을 먼저 보완한 뒤 구현한다. |
| API나 데이터 구조로 표현할 수 없음 | OpenAPI 또는 데이터 모델을 같은 PR에서 수정한다. |
| 구현이 명세와 다름 | 합의된 변경이 없다면 구현을 고친다. |
| Figma가 기존 동작과 다름 | 시각 차이는 Figma를 따르고, 제품 동작 차이는 Feature에서 다시 결정한다. |
| AI 초안에 버그나 보안 문제가 있음 | 영역 책임 개발자가 수정하고 회귀 테스트를 추가한다. |

발견한 문제를 개인 메모나 채팅에만 남기지 않는다. 제품 결정은 Feature의 `결정 기록`, 구현 작업은 Task나 PR, 재현 가능한 결함은 Bug 이슈에 남긴다.

## Production-ready 완료 기준

담당 기능은 다음 조건을 모두 만족해야 `Done`으로 본다.

- Feature의 수용 조건과 연결된 요구사항을 충족한다.
- 정상 흐름뿐 아니라 빈 상태, 권한 오류, 중복 요청, AI 실패와 재시도를 처리한다.
- 다른 사용자의 데이터를 조회하거나 참조할 수 없다.
- API 변경은 OpenAPI와 계약 테스트에, 데이터 변경은 `schema.sql`과 데이터 문서에 반영한다.
- SQLite FK가 켜진 상태에서 초기 schema 생성과 통합 테스트가 통과한다.
- 외부 AI나 저장소 호출을 DB 쓰기 트랜잭션 안에서 기다리지 않는다.
- 로그와 테스트 fixture에 비밀값이나 실제 사용자 기록이 없다.
- Figma와 프로토타입에 정의된 주요 상태를 실제 화면에서 확인했다.
- 해당 기능을 포함한 P0 E2E 순환이 다시 통과한다.

## 산출물의 기준

| 질문 | 기준 자료 |
| --- | --- |
| 왜 만드는가 | 제품 브리프와 요구사항 |
| 사용자가 무엇을 할 수 있는가 | GitHub Feature 기능명세 |
| 화면이 어떻게 보여야 하는가 | 승인된 Figma |
| 구현 전 흐름을 어떻게 빠르게 검증하는가 | HTML 프로토타입 |
| 프론트엔드와 서버가 무엇을 주고받는가 | OpenAPI |
| 무엇을 어떻게 저장하는가 | 데이터 모델과 `schema.sql` |
| 실제로 동작하는가 | 코드와 자동화 테스트 |

HTML 프로토타입은 흐름 검증 도구이며 실제 제품 코드가 아니다. 통합 초안의 실제 화면은 초기에는 테스트 하네스 수준일 수 있지만, 완료 전에는 승인된 Figma를 반영해야 한다. Figma는 시각 원본이지만 서버 동작을 결정하지 않는다. 코드는 문서와 다른 제품 결정을 몰래 만들 수 없다.
