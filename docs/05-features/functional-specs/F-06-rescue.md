# F-06 AI Rescue

## 1. 사용자가 얻는 결과

사용자는 피부가 불편해진 순간 자연어 대화를 시작하고, 저장된 루틴 변화와 검증된 외부 근거를 바탕으로 무엇부터 확인할지와 다음에 사용할 루틴 하나를 제안받는다. AI는 진단하거나 범인을 확정하지 않고, 실제 루틴 변경은 사용자가 선택한다.

## 2. 진입점과 시작 기준

진입점:

- 홈의 `불편함이 생겼어요`
- 7일 결과의 `불편했어요`
- 현재 루틴·내 화장품의 동일 버튼
- 기존 Rescue 대화 이어가기

새 Rescue는 시작 시점의 current routine ID와 stable routine ID를 고정한다. 분석 도중 루틴이 바뀌면 기존 case에는 소급 반영하지 않고 `현재 루틴이 바뀜`을 표시한다.

한 사용자는 `CONVERSATION`, `ANALYZING`, `READY` 상태의 Rescue를 한 개만 가진다. 열린 case가 있으면 새 case 대신 기존 대화를 연다. `처음부터 다시 말하기`를 선택하면 기존 case를 `CLOSED`로 만들고 새 case를 시작한다.

## 3. 대화 UX 계약

- 이전 사용자·AI 메시지를 삭제하거나 다른 페이지로 교체하지 않는다.
- 진행률, `1/4`, 단계 번호를 표시하지 않는다.
- 자유 입력이 기본이며 예/아니오처럼 빠른 답만 선택 버튼을 함께 준다.
- 사실을 모를 수 있는 질문에는 `잘 모르겠어요`를 함께 제공한다.
- 새 응답과 분석 상태는 대화 아래에 붙는다.
- AI는 저장된 루틴·제품·이전 답을 다시 묻지 않는다.
- 사용자가 사실을 수정하면 정정 메시지를 남기고 이후 분석은 최신 확인값을 사용한다.
- job 처리 중에도 사용자는 지금까지의 대화와 확인된 변경 목록을 볼 수 있다.

## 4. 대화에서 수집하는 최소 정보

AI는 다음 정보 중 분석에 필요한 빈칸만 한 번에 하나씩 묻는다.

| 정보 | 저장 형태 | 용도 |
| --- | --- | --- |
| 불편 표현 | 사용자 원문 + AI 구조화 문장 | 현재 질문 설명 |
| 시작 시점 | 정확한 날짜 또는 상대 표현 원문 | 루틴 변경과 시간 관계 비교 |
| 실제 사용 | 기록된 루틴과 다른 부분 | 분석 입력 보정 |
| 최근 다른 변화 | 사용자 자유 문장 | 화장품 변화만으로 단정하지 않기 |
| 심함·빠른 악화 여부 | 사용자 self-report | 안전 경계 분기 |

증상을 의료 용어 enum으로 확정하지 않는다. AI 구조화 문장은 검색 질의를 만드는 임시 해석이며 원문과 함께 저장한다.

사용자가 `잘 모르겠어요`라고 답하면 AI는 더 쉽게 관찰할 수 있는 질문이 있을 때만 한 번 바꿔 묻는다. 다시 모르겠다고 하거나 답이 없으면 해당 값은 미확인으로 남긴다. 안전 경계 질문의 미응답을 `심하지 않음`으로 바꾸지 않으며, 시점·실사용이 미확인이면 후보의 `uncertainty`에 반영한다.

## 5. 안전 경계

AI는 응급도를 판정하지 않는다. 사용자가 직접 `심하다` 또는 `빠르게 악화된다`고 답한 경우에만 `safetyBoundaryReached=true`로 둔다.

이 경우:

1. 제품별 확인 순위와 권장 루틴 생성을 중단한다.
2. 제품 사용 조정만으로 해결하려 하지 말고 신속히 전문가 도움을 받으라는 고정 안내를 보여준다.
3. 질환명·알레르기·응급도·진료과를 제시하지 않는다.
4. 지금까지의 사용자 원문과 루틴 변경 목록은 볼 수 있다.
5. 사용자가 새 대화에서 안전 경계 답을 정정하기 전에는 분석 재시도를 제공하지 않는다.

## 6. 변경 기준 만들기

### 안정 루틴이 있을 때

서버가 stable과 Rescue 시작 routine을 비교해 다음 변화를 계산한다.

- 제품 추가·삭제
- 아침/저녁 이동
- 순서 변화
- 빈도 변화

AI는 변경 목록을 자연어로 설명하고 사용자가 실제 사용과 다른 항목을 수정한다. 수정 원문과 `userConfirmed`를 저장한다.

### 안정 루틴이 없을 때

- 기준점이 약하다고 첫 분석 카드에 표시한다.
- 현재 루틴과 과거 기록 중 가장 오래 변경 없이 사용했고 불편 기록이 없는 제품을 보조 기준으로 삼을 수 있다.
- 모든 순위의 `basisStrength`는 `WEAK_NO_STABLE_ROUTINE`이다.

### 현재 루틴이 없을 때

- `basisStrength=NONE_NO_ROUTINE`이다.
- 자유 기록과 일반 안전 안내만 제공한다.
- 제품별 확인 순위와 개인화 루틴은 생성하지 않는다.

## 7. 조사 후보와 확인 순위

### 7.1 후보 집합

안정 루틴 이후 달라진 제품·사용 조건만 기본 후보로 만든다. 변경 없는 안정 루틴 제품은 반대 근거와 다음 루틴 유지 후보로만 사용할 수 있다.

### 7.2 AI 조사 결과

각 후보마다 AI가 다음 신호와 근거를 schema로 반환한다.

| 신호 | 범위 | 의미 |
| --- | --- | --- |
| `temporal_fit` | 0~3 | 사용자 진술 시점과 해당 변경의 가까움 |
| `exposure_change` | 0~3 | 새 추가·재사용·빈도 증가처럼 노출 조건이 달라진 정도 |
| `evidence_relevance` | 0~3 | 질문과 직접 관련된 허용 외부 근거의 정도 |
| `personal_recurrence` | 0~2 | 같은 제품·비슷한 조건의 사용자 과거 불편 기록 |
| `opposing_evidence` | 0~-2 | 같은 조건에서 불편 없음 등 반대 개인 기록 |
| `uncertainty` | 0~-2 | 버전·시점·실사용·근거 부족 |

각 1점 이상 또는 음수 신호는 출처나 개인 기록 참조가 있어야 한다. 서버는 참조가 없는 신호를 0으로 만들고 감사 로그에 남긴다.

### 7.3 서버 순위

- 서버가 검증된 신호를 합산해 `reviewPriorityScore`를 계산한다.
- 점수는 사용자에게 숫자·확률로 보여주지 않는다.
- 점수 내림차순, 동점이면 `시간 적합성 → 노출 변화 → 정보 완전성 → myProductId` 순이다.
- 최대 3개를 `먼저 확인할 변경`으로 보여준다.
- 각 순위에는 먼저 보는 이유, 반대 근거, 모르는 점과 출처가 반드시 함께 있다.
- 순위는 원인 확률이 아니라 확인 범위를 줄이기 위한 행동 순서라고 표시한다.

## 8. 권장 루틴 생성

AI는 검증된 순위와 stable routine을 입력으로 다음 루틴 하나를 제안한다.

1. stable routine이 있으면 그 제품·순서·빈도를 기본값으로 복사한다.
2. 1순위 변경 항목을 우선 제외하거나 stable 당시 값으로 되돌린다.
3. 서로 관련된 동시 변경이라 하나만 되돌리면 비교가 불가능한 경우에만 여러 항목을 함께 조정하고 이유를 표시한다.
4. 변경 없는 안정 제품은 공식 주의 근거가 새로 확인되지 않는 한 유지한다.
5. 새 제품을 추가해 해결하려는 제안은 하지 않는다.
6. stable routine이 없으면 검증된 현재 제품 중 과거 불편 기록이 없고 사용 조건이 명확한 최소 조합을 제안할 수 있다.
7. 제품, 아침/저녁, 위치, 빈도를 모두 반환한다.
8. 서버는 소유 제품, verified 버전, item 유일성·순서, 제안 근거와 금지 표현을 검증한다.

AI 제안에는 `빼는 것`, `유지하는 것`, `바뀐 순서`, `왜 이렇게 제안하는지`, `정보 부족`을 표시한다.

## 9. 사용자 선택과 상태 전이

| 선택 | Rescue | 루틴 | 7일 |
| --- | --- | --- | --- |
| 이 루틴으로 시작 | `CLOSED/APPLIED` | 독립된 새 `RESCUE_PLAN` 버전을 current로 생성 | 새 DAY 1 |
| 직접 수정 후 시작 | `CLOSED/APPLIED_EDITED` | 수정한 내용으로 새 버전 | 새 DAY 1 |
| 기록만 남기기 | `CLOSED/RECORD_ONLY` | current 변경 없음 | 기존 일정 유지 |
| 대화 닫기 | 열린 상태 유지 | 변경 없음 | 기존 일정 유지 |

AI는 사용자의 선택 전에 제품을 내 화장품에서 삭제하거나 루틴을 바꾸지 않는다. Rescue 적용 루틴도 `복구 중` 같은 별도 상태를 갖지 않는 일반 current routine이다.

## 10. 실패·예외 계약

| 상황 | 결과 |
| --- | --- |
| AI 분석 실패 | 메시지·확인된 변경 보존, 재시도; 현재 루틴 유지 |
| 일부 출처 검증 실패 | 해당 신호 제거, 남은 근거로 재계산; 모두 제거되면 정보 부족 |
| 분석 중 current 변경 | 기존 시작 기준을 표시하고 새 루틴으로 새 Rescue 시작 선택 제공 |
| 제안에 보유하지 않은 제품 | plan 전체 거절, 재생성 |
| apply 중 current 충돌 | `409 ROUTINE_VERSION_CONFLICT`, 제안과 사용자 수정안 보존 |
| 동일 apply 재시도 | 같은 routine ID 반환 |
| 안전 경계 도달 | 제품 순위·plan 없음, 전문가 안내와 기록만 제공 |

## 12. 수용 시나리오

1. **Given** 마지막 안정 이후 제품 2개가 추가된 current, **When** Rescue를 시작하면, **Then** 두 제품과 다른 순서·빈도 변화만 기본 후보로 계산한다.
2. **Given** 사용자가 심하거나 빠르게 악화된다고 답함, **When** 다음 응답을 만들면, **Then** 순위와 plan 없이 고정 안전 안내를 제공한다.
3. **Given** 1순위 후보에 반대 개인 기록이 있음, **When** 결과를 보여주면, **Then** 먼저 보는 이유와 함께 반대 기록도 표시한다.
4. **Given** 권장 루틴, **When** 사용자가 직접 수정해 적용하면, **Then** 수정본이 독립된 current routine과 새 DAY 1이 된다.
5. **Given** AI 장애, **When** 앱을 다시 열면, **Then** 이전 모든 메시지와 확인된 변경을 그대로 보고 재시도할 수 있다.
6. **Given** 사용자가 발생 시점이나 실제 사용을 모름, **When** 추가 질문에도 답하지 못하면, **Then** 값을 추정하지 않고 해당 후보의 정보 부족과 약한 근거를 표시한다.
