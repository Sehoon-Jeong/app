# F-08 AI·보안·작업 기반

## 1. 목적

AI가 자연어를 다루더라도 사용자 소유권, 비교 사실, 상태 전이와 실제 저장 결과는 서버가 통제한다. AI 실패는 이미 입력한 제품·루틴·결과·Rescue 메시지를 지우지 않는다.

## 2. 우선순위 범위

| 우선순위 | 결과 | 요구사항 |
| --- | --- | --- |
| P0 | 자연어 구조화·서버 검증·기록 보존·소유권·트랜잭션·stale plan 통제 | AI-01~02, AI-04, SEC-01~02, OPS-01~03 |
| P1 | 외부 근거 snapshot과 범용 request/run/job·worker lease | AI-03, AI-05 |
| P2 | OCR·처음부터 추천하는 AI 작업 | PRD-02~03, REC-01~04 |

## 3. P0 계약

### 3.1 역할 경계

| AI | 서버 |
| --- | --- |
| 자연어에서 현재 질문에 필요한 의미 추출 | 인증과 모든 개인 ID의 소유권 확인 |
| 결과를 크게 바꾸는 최소 추가 질문 | 질문 가능한 상태와 횟수 결정 |
| 서버가 계산한 비교·순위·계획 설명 | 루틴 차이, 후보 집합, 순위와 상태 전이 계산 |
| 구조화된 제안 반환 | schema·ID·금지 표현 검증과 실제 저장 |

AI 응답만으로 제품·루틴·assessment·stable period·Rescue 적용 상태를 변경할 수 없다.

### 3.2 P0 요청 처리 순서

1. 사용자의 제품·루틴·결과 또는 Rescue 메시지를 먼저 짧은 트랜잭션으로 저장한다.
2. 필요한 개인 데이터만 allowlist로 복사해 입력 snapshot을 만든다.
3. 트랜잭션을 끝낸 뒤 OpenAI API를 호출한다.
4. 서버가 JSON schema, 참조 ID 소유권, 의료 금지 표현과 기능별 규칙을 검증한다.
5. 검증된 설명만 공개한다. 실패하면 사용자 기록을 유지하고 고정 설명 또는 재시도를 제공한다.
6. Rescue plan 적용 직전에 `baseRoutineVersionId`와 현재 ACTIVE 루틴을 다시 비교한다. 다르면 `STALE`로 막는다.

P0는 단일 API 인스턴스 안의 단순 executor여도 된다. AI 호출을 기다리며 SQLite 쓰기 트랜잭션이나 사용자 전역 잠금을 유지하지 않는다.

### 3.3 최소 입력 원칙

| 데이터 | 기본 | 조건 |
| --- | --- | --- |
| 사용자 ID·이메일·토큰 | 금지 | 공급자 요청에 포함하지 않음 |
| 현재 질문 원문 | 포함 | 해당 대화 turn만 |
| 현재·안정 루틴 | 기능별 포함 | 필요한 필드만 |
| 과거 개인 기록 | 관련 기록만 | 외부용 대체 참조키 사용 |
| 제품 메모·이미지 원문 | 제외 | 해당 요청에서 사용자가 명시적으로 허용할 때만 |

프롬프트·로그·fixture에 실제 사용자 기록이나 비밀값을 넣지 않는다. 운영 로그는 내부 요청 ID, 모델, prompt version, 지연, token과 오류 코드만 남긴다.

### 3.4 출력 검증

1. JSON과 지원 schema version
2. 요청 snapshot과 analysis type
3. 제품·내 화장품·루틴·개인 기록의 존재와 소유권
4. 기능별 허용 값과 참조 관계
5. 진단·범인 단정·적합 확률 등 금지 표현
6. 서버 계산 결과와 AI 설명의 일치

하나라도 실패하면 해당 출력을 상태 변경에 쓰거나 사용자에게 완성 결과처럼 노출하지 않는다.

### 3.5 오류와 대체 경로

| 코드 | 의미 | 사용자 경로 |
| --- | --- | --- |
| `AI_PROVIDER_TIMEOUT` | 공급자 지연 | 저장된 입력으로 재시도 |
| `AI_OUTPUT_INVALID` | JSON·schema 위반 | 고정 설명 또는 재시도 |
| `AI_REFERENCE_INVALID` | 잘못된 제품·개인 ID | 결과 폐기 |
| `AI_SAFETY_BOUNDARY` | Rescue 안전 경계 | 제품 분석 중단·전문가 확인 안내 |
| `INPUT_STALE` | 기준 루틴 변경 | 최신 루틴으로 새 계획 생성 |

### 3.6 P0 수용 시나리오

1. **Given** 루틴 저장 완료, **When** AI timeout, **Then** 루틴과 DAY 7 일정은 남는다.
2. **Given** 존재하지 않거나 다른 사용자 product ID를 AI가 반환, **When** 검증, **Then** 결과를 공개하거나 적용하지 않는다.
3. **Given** Rescue plan 생성 뒤 ACTIVE 루틴 변경, **When** 적용, **Then** `INPUT_STALE`로 거절한다.
4. **Given** 메모 포함 동의 없음, **When** AI 입력을 만들면, **Then** 메모가 snapshot과 공급자 요청에 없다.

## 4. P1 계약 · 외부 근거와 범용 비동기 실행

### 4.1 분석과 실행 이력

| 엔티티 | 책임 |
| --- | --- |
| `analysis_request` | 논리적 요청, 입력 snapshot·hash, 최종 채택 run |
| `analysis_run` | 한 번의 모델 시도, 모델·prompt·원본 출력·검증 오류·token |
| `ai_job` | 대기·실행·lease·heartbeat·재시도 운영 |

모델·프롬프트·출력·검증 결과는 request가 아니라 각 run에 속한다. 재시도는 과거 run을 덮지 않는다. worker가 죽으면 만료된 lease를 다른 worker가 회수할 수 있다.

### 4.2 외부 근거

허용 출처는 브랜드·제조사, 정부·규제기관, 공식 성분 DB와 원 논문이다. AI는 주장, 지지·반대·불확실 관계, 적용 제품 버전과 출처를 반환한다.

서버는 URL·출처 유형·제품 버전 연결과 원료 근거의 과장을 검증한다. 허용 근거는 URL 정체성인 `evidence_source`와 확인 당시 내용인 `evidence_snapshot`으로 나눠 저장한다. 블로그·리뷰·커뮤니티는 제품 사실 근거로 저장하지 않는다.

### 4.3 재시도·멱등성

- 동일 사용자·작업 종류·입력 hash에 열린 job이 있으면 재사용한다.
- provider timeout, rate limit과 invalid JSON만 자동 1회 재시도한다.
- 쓰기 API의 같은 멱등 키·같은 body는 최초 결과를 반환하고, 다른 body는 409다.
- 오래된 AI 출력은 최신 상태를 덮지 않는다.

## 5. P2 계약 · 확장 작업 종류

P2에서 `RECEIPT_OCR`과 `RECOMMENDATION` 작업을 활성화한다. 영수증 원본은 OCR 요청에만 보내고 다른 개인 맥락과 결합하지 않는다. 추천 후보도 서버가 실제 카탈로그 ID·국내 판매 상태와 제외 조건을 검증한 뒤에만 공개한다.

연결 요구사항: AI-01~05, SEC-01~02, OPS-01~03
