# F-02 카탈로그·내 화장품

## 1. 사용자가 얻는 결과

사용자는 제품명으로 찾거나 이름을 직접 입력해 화장품을 등록한다. 등록은 내 화장품만 바꾸며 현재 루틴은 자동으로 바꾸지 않는다.

## 2. 우선순위 범위

| 우선순위 | 결과 | 요구사항 |
| --- | --- | --- |
| P0 | 큐레이션 제품 검색·이름 직접 입력·내 화장품 등록 | PRD-01, CAT-03 |
| P1 | 실제 출시판·근거 snapshot·메모·삭제·제품별 이력 | CAT-01~05, PRD-04~06 |
| P2 | 영수증 OCR·가격·판매처 | PRD-02~03, CAT-06 |

P0는 국내 전체 카탈로그를 요구하지 않는다. 테스트 사용자 제품 또는 30~50개 제품만 미리 등록하고, 검색되지 않으면 이름만으로 계속할 수 있게 한다.

## 3. P0 계약

### 3.1 저장 단위

| 구분 | 필수 값 | 쓰임 |
| --- | --- | --- |
| 확인 제품 | 브랜드, 제품명, 짧은 옵션, `productVersionId` | 큐레이션된 제품 사실과 연결 |
| 직접 입력 제품 | 사용자가 입력한 제품명 | 제품 사실을 모르는 상태로 실제 사용 기록 |
| 내 화장품 | 사용자, 확인 제품 또는 직접 입력 이름, 등록 시각 | 루틴에서 선택하는 사용자 소유 항목 |

직접 입력 제품은 `UNVERIFIED`다. 등록과 루틴 사용 사실은 근거로 쓸 수 있지만 성분·기능·사용법을 확인된 사실처럼 설명하지 않는다.

### 3.2 검색·직접 입력·등록 흐름

1. 사용자가 브랜드나 제품명 일부를 입력한다.
2. 서버는 P0 큐레이션 목록에서 최대 20개를 반환한다.
3. 사용자가 결과를 선택하면 브랜드·제품명·옵션과 확인 상태를 보여준다.
4. 결과가 없으면 검색어를 유지한 채 `이 이름으로 추가`를 제공한다.
5. `내 화장품에 추가`를 누르면 `user_product`를 한 번 만든다.
6. 새 제품은 미사용 화장품에 나타나며 현재 루틴은 그대로다.
7. 루틴 편집 중 등록했다면 같은 편집안으로 돌아가 새 제품을 선택할 수 있다.

같은 요청의 재전송은 멱등 키로 한 항목만 만든다. 같은 확인 제품을 이미 가진 경우 기존 항목을 먼저 보여준다.

### 3.3 P0 화면

내 화장품은 세 묶음만 사용한다.

| 묶음 | 포함 조건 |
| --- | --- |
| 미사용 화장품 | 현재 루틴과 마지막 안정 루틴에 모두 없음 |
| 현재 루틴 | ACTIVE 루틴에 포함 |
| 마지막 안정 루틴 | 열린 stable period의 루틴에 포함 |

제품 하나가 현재 루틴과 마지막 안정 루틴 양쪽에 있을 수 있다. 이 묶음은 재고 상태가 아니라 루틴 포함 관계다.

### 3.4 P0 실패·예외

| 상황 | 사용자 결과 |
| --- | --- |
| 검색 0건 | 검색어 유지, 이름 직접 입력 제공 |
| 미확인 제품 | `제품 정보 미확인` 표시, 사용 기록은 허용 |
| 중복 탭·네트워크 재시도 | 최초 등록 결과 재사용 |
| 다른 사용자 항목 접근 | 존재 여부를 드러내지 않는 404 |

### 3.5 P0 API·데이터

| 행동 | API | 데이터 |
| --- | --- | --- |
| 검색·상세 | `GET /products`, `GET /products/{productVersionId}` | catalog read |
| 내 화장품 조회·등록 | `GET/POST /me/products` | `user_product` |

### 3.6 P0 수용 시나리오

1. **Given** 큐레이션 제품, **When** 등록하면, **Then** 미사용 화장품에만 나타나고 현재 루틴은 바뀌지 않는다.
2. **Given** 검색 결과가 없음, **When** 이름으로 추가하면, **Then** 루틴에는 넣을 수 있지만 제품 사실은 AI 근거에서 제외된다.
3. **Given** 사용자 A의 내 화장품 ID, **When** 사용자 B가 조회하면, **Then** 존재 여부를 구분하지 않는 404를 받는다.

## 4. P1 계약 · 검증된 카탈로그와 제품 관리

### 4.1 실제 출시판

AI와 제품 사실이 참조하는 단위는 이름만 같은 제품군이 아니라 `product_version`이다. 같은 이름이어도 처방·용량·포장·시장 조건이 달라지면 별도 출시판으로 관리한다.

검증 상태와 판매 상태는 분리한다.

| 검증 상태 | 의미 | 제품 사실 사용 |
| --- | --- | --- |
| `VERIFIED` | 출시판과 근거 확인 | 가능 |
| `UNVERIFIED` | 아직 확인하지 못함 | 불가 |
| `CONFLICTED` | 출처끼리 충돌 | 해결 전 불가 |

| 판매 상태 | 의미 | 신규 탐색 |
| --- | --- | --- |
| `ACTIVE` | 현재 판매 확인 | 노출 |
| `DISCONTINUED` | 판매 종료 확인 | 제외, 과거 기록 유지 |
| `UNKNOWN` | 판매 여부 미확인 | 검색에는 상태 표시, 추천 제외 |

### 4.2 제품 사실과 근거

- 출처 우선순위는 브랜드·제조사, 정부·규제기관, 공식 성분 DB, 원 논문이다.
- `evidence_source`는 URL의 정체성, `evidence_snapshot`은 확인 당시 내용과 hash를 보존한다.
- 하나의 `product_fact`는 여러 snapshot 근거를 가질 수 있다.
- 표시 전성분은 원문 목록과 순서를 보존한다. 성분 이름 동일성만 사전화하며 피부 영향 enum은 만들지 않는다.
- 블로그·리뷰·커뮤니티는 제품 사실로 저장하지 않는다.

### 4.3 메모·삭제·제품 기록

- 메모는 최신 revision을 표시하며 AI에는 사용자가 해당 요청에서 허용할 때만 보낸다.
- 현재 루틴 제품 삭제는 막고 루틴 편집으로 보낸다.
- 삭제해도 과거 루틴 item과 당시 제품 정보는 보존한다.
- 제품 상세는 포함됐던 루틴과 루틴 전체 결과를 보여준다. 이를 제품 단독 결과로 표현하지 않는다.

P1 API는 `PUT /me/products/{myProductId}/memo`, `DELETE /me/products/{myProductId}`와 제품 이력 조회를 추가한다.

## 5. P2 계약 · 영수증 OCR과 구매 정보

1. 사용자가 영수증 이미지 하나를 올린다.
2. 원본을 Object Storage에 저장하고 쓰기 트랜잭션을 끝낸다.
3. AI는 줄별 브랜드·제품명·옵션 후보만 추출한다.
4. 서버가 카탈로그 후보와 연결하고 사용자가 각 줄을 확정하거나 제외한다.
5. 확정한 제품만 내 화장품에 추가한다. 루틴은 자동으로 바꾸지 않는다.

OCR 실패 시 원본과 사용자의 확정 내용은 유지하고 재시도 또는 제품명 검색을 제공한다. 가격·판매처는 확인 시각과 함께 참고로만 표시하며 제품 의견·추천 순위에는 사용하지 않는다.

연결 요구사항: CAT-01~06, PRD-01~06
