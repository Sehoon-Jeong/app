# F-03 제품 의견·추천

## 1. 사용자가 얻는 결과

- `이거 사볼까?`: 외부에서 본 한 제품을 지금 자신의 맥락에서 살 이유와 망설일 이유를 AI와 대화로 확인한다.
- `제품 추천받기`: 원하는 변화를 자연어로 말하고 실제 국내 제품 후보를 최대 5개 받는다.

두 결과 모두 피부 적합·안전·효능 판정이 아니다. 결과는 구매 판단을 돕고, 구매 후 내 화장품과 루틴으로 연결하기 위한 설명 가능한 후보 목록이다.

## 2. 공통 입력 스냅샷

분석 시작 시 다음 입력을 복사해 `analysis.input_snapshot_json`에 고정한다. 분석 도중 원본이 바뀌어도 진행 중 결과에는 소급 반영하지 않는다.

| 입력 | 포함 조건 | 권한·품질 규칙 |
| --- | --- | --- |
| 사용자의 현재 요청 | 항상 | 원문 보존 |
| 현재 루틴 | 있으면 | 제품·시간대·순서·빈도 |
| 마지막 안정 루틴 | 있으면 | 현재 루틴과 같아도 별도 참조 |
| 내 화장품 | 항상 | 삭제 제품 제외, 버전 `VERIFIED`만 분석 |
| 과거 결과·Rescue | 관련 기록만 | 루틴 전체 관찰과 제품 단독 경험을 구분 |
| AI 기억 | 삭제되지 않은 항목만 | 사용자가 확인한 현재 문장 |
| 제품 메모 | `includeMemo=true`일 때만 | 요청 대상 또는 비교 제품 메모만 |
| 제품·성분 외부 근거 | 질문과 관련된 것만 | 허용 출처, 적용 버전, 확인 시각 필수 |

피부 고민과 원하는 변화를 enum으로 변환해 영구 저장하지 않는다. AI는 현재 요청에서 의미 단위의 문장으로 해석하고, 각 해석에 사용자 원문 위치를 연결한다.

## 3. 공통 조사·검증 파이프라인

1. 서버가 인증, 제품 ID, 사용자 기록 소유권과 입력 스냅샷을 확정한다.
2. 제품 의견은 대상 제품 버전, 추천은 최대 20개의 조사 후보를 AI에 요청한다.
3. AI는 허용된 웹 출처에서 현재 질문과 직접 관련된 주장만 수집한다.
4. AI는 `주장`, `지지/반대/불확실`, `대상 제품 버전`, `출처`, `개인 기록 참조`, `설명`을 schema에 맞게 반환한다.
5. 서버는 실제 카탈로그 ID, 국내 판매 범위, 버전 상태, URL·출처 유형, 개인 기록 소유권과 금지 표현을 검증한다.
6. 검증되지 않은 주장과 후보는 제거한다. 제거 후 0개도 정상 결과다.
7. 서버 규칙이 결론과 후보 순서를 계산한다.
8. AI는 계산된 결론·순서를 바꾸지 않고 사용자에게 자연어로 설명한다.

### 허용 근거 강도

| 등급 | 근거 | 사용할 수 있는 표현 |
| --- | --- | --- |
| A | 해당 제품 버전의 공식 사용법·표시 정보, 같은 완제품 사람 대상 연구 | 해당 제품의 확인된 사실 |
| B | 정부·공식 DB, 관련 원료의 원 논문 | 관련 가능성·확인할 점 |
| C | 사용자의 정확한 제품·루틴 결과 | 개인의 과거 관찰 |
| D | 비슷한 제형·제품군의 개인 경험 | 비교 참고, 패턴으로 표현 금지 |

리뷰·커뮤니티·판매량·인기·가격은 결론과 순위에 사용하지 않는다.

## 4. “이거 사볼까?”

### 4.1 진입 조건

- 사용자가 카탈로그의 `VERIFIED` 제품 버전 하나를 선택한다.
- 구매 목적이 비어 있거나 너무 넓으면 AI가 결과를 크게 바꿀 질문을 최대 2개까지 순차적으로 묻는다.
- 모든 질문에 `잘 모르겠어요`를 제공한다. AI는 더 쉬운 관찰 질문이 있으면 한 번 바꿔 묻고, 다시 모르거나 답하지 않아도 분석을 계속하며 `목적 정보 부족`을 결과에 표시한다.

### 4.2 결론 계산

AI는 검증 가능한 근거를 다음 판정값으로 구조화하고 서버는 아래 순서대로 결론을 정한다.

| 판정값 | 범위 | 의미 |
| --- | --- | --- |
| `goal_relevance` | 0~3 | 현재 목적과 제품의 확인된 사용법·표시 정보가 얼마나 직접 연결되는지 |
| `overlap` | 0~2 | 현재 루틴·미사용 보유품과 확인된 역할이 겹치는 정도 |
| `evidence_completeness` | 0~2 | 결론에 필요한 버전·공식 정보·출처가 갖춰진 정도 |
| `personal_comparison` | 0~1 | 직접 또는 비교 가능한 개인 기록이 있는지. 적합 확률로 쓰지 않음 |

결론 우선순위:

1. `evidence_completeness=0`이면 `INSUFFICIENT`.
2. 정보는 충분하지만 `goal_relevance=0`이면 `LOW_RELEVANCE`.
3. `overlap=2`이고 새로 더해지는 확인된 차이가 없으면 `OVERLAP`.
4. `goal_relevance>=1`이고 위 조건에 해당하지 않으면 `CONSIDER`.

`personal_comparison`은 결론을 단독으로 바꾸지 않는다. 설명의 개인화와 관찰할 점에만 사용한다.

### 4.3 결과 구조

| 필드 | 필수 | 규칙 |
| --- | --- | --- |
| 결론 코드·문구 | 필수 | `CONSIDER`, `OVERLAP`, `LOW_RELEVANCE`, `INSUFFICIENT` 중 하나 |
| 지금 볼 이유 | 0개 이상 | 검증된 지지 근거 참조 |
| 망설일 이유 | 0개 이상 | 중복·반대 근거 참조 |
| 아직 모르는 것 | 필수 | 0개면 `현재 확인한 범위에서 별도 정보 부족 없음`이라고 범위를 명시 |
| 내 루틴 변화 | 루틴이 있으면 필수 | 추가 시 시간대·예상 위치·겹침. 실제 루틴 자동 변경 금지 |
| 개인 경험 연결 | 관련 기록이 있으면 | 날짜·루틴 버전·결과 범위를 표시 |
| 출처 | 주장마다 | 제목·기관·URL·게시일·확인일 |
| 면책 문구 | 필수 | 구매·적합·안전·효능 보장이 아님 |

### 4.4 후속 행동

- 채팅 질문은 같은 `conversationId`와 입력 스냅샷을 기본으로 이어간다.
- 사용자가 `지금 루틴 기준으로 다시 봐줘`처럼 최신 정보 사용을 명시하면 새 분석을 만들고 이전 결과를 덮지 않는다.
- `샀어요`는 해당 버전을 내 화장품에 `UNUSED`로 추가한다.
- `찜`은 wishlist에 추가한다.
- `비슷한 제품`은 별도 목록을 최대 5개 표시한다. 제품 채팅으로 자동 이동하지 않는다.
- 이미 가진 제품은 `보유 중`으로 표시하고 재등록 버튼을 비활성화한다.

## 5. “제품 추천받기”

### 5.1 추가 질문 규칙

AI는 다음 중 하나가 후보의 포함·제외를 바꿀 때만 한 번에 한 질문을 한다.

- 원하는 변화가 해석되지 않음
- 피하고 싶은 제형·향·사용 조건이 불명확함
- 어느 시간대 또는 기존 제품 대체인지가 후보를 크게 바꿈

추가 질문은 최대 3회다. 이후에는 현재 정보로 0~5개를 반환하고 부족한 맥락을 표시한다.

`잘 모르겠어요`는 제외 조건이나 피부 상태를 추정하는 신호가 아니다. AI는 `민감성인가요?`처럼 분류를 다시 요구하지 않고 `향이 강한 제품을 썼을 때 불편했던 적이 있나요?`처럼 사용자가 기억할 수 있는 관찰로 한 번만 바꿔 묻는다. 그래도 모르면 해당 조건을 `정보 부족`으로 두며 추천 완료를 막지 않는다.

### 5.2 후보 게이트

아래 하나라도 실패하면 후보에서 제외한다.

1. 국내 판매 범위 제품이 아님
2. 카탈로그 버전이 `VERIFIED`가 아님
3. 허용 출처로 현재 목적과의 관련성을 한 건도 설명할 수 없음
4. 사용자가 명시한 제외 조건과 충돌함
5. 같은 제품 버전을 이미 보유함
6. 동일 제품이 후보 목록에 중복됨

### 5.3 순위 계산

게이트를 통과한 후보에 서버가 다음 점수를 적용한다.

| 항목 | 점수 | 계산 기준 |
| --- | --- | --- |
| 목적 직접성 | 0~3 | 검증된 A/B 근거가 요청 문장과 직접 연결되는 정도 |
| 현재 루틴에서의 새 차이 | 0~2 | 높은 중복 0, 일부 차이 1, 확인 가능한 새 역할 2 |
| 근거 완전성 | 0~2 | 버전·공식 정보·출처의 완전성 |
| 개인 비교 가능성 | 0~1 | 관련 개인 기록 존재. 잘 맞을 가능성이 아님 |
| 중요 정보 부족 | 0~-2 | 향·사용법·버전 등 질문에 중요한 미확인 정보 |

총점 내림차순으로 정렬한다. 동점이면 `근거 완전성 → 목적 직접성 → 카탈로그 최신 확인 시각 → productVersionId` 순으로 결정한다. 최대 5개만 반환하며 최소 개수는 없다.

### 5.4 후보 표시

각 후보는 순위, 제품, 추천 이유, 망설일 이유, 정보 부족, 현재 루틴에서 달라지는 점, 확인할 점과 근거를 가진다. 1위가 더 잘 맞는다는 문구는 사용하지 않는다. 순위는 현재 질문을 설명하기 쉬운 순서다.

## 6. 실패·예외 계약

| 상황 | 결과 |
| --- | --- |
| AI 검색 실패 | job 실패, 입력 보존, 재시도와 카탈로그 사실만 보기 제공 |
| 후보 0개 | 빈 결과와 제외 이유 요약, 조건을 고쳐 다시 요청 가능 |
| 출처 일부 실패 | 해당 주장 제거 또는 `정보 부족`, 나머지 결과 유지 |
| 분석 중 루틴 변경 | 기존 스냅샷 결과임을 표시, 최신 기준 다시 분석 제공 |
| 제품 버전 불확실 | 의견·추천 생성 차단, 버전 확인 흐름 제공 |
| 금지 표현·schema 위반 | 결과 공개 안 함, job 실패 코드와 재시도 제공 |
| 같은 요청 재제출 | 동일 입력 hash의 열린 job 재사용 |

## 7. 상태·API·데이터 변화

| 행동 | API | 상태 변화 |
| --- | --- | --- |
| 제품 의견 시작 | `POST /product-opinions` | analysis·job·conversation 생성 |
| 의견 조회 | `GET /product-opinions/{opinionId}` | 검증된 결과 조회 |
| 추천 시작·조회 | `POST /recommendations`, `GET /recommendations/{recommendationId}` | job 또는 추가 질문·후보 조회 |
| 후속 질문 | `POST /conversations/{conversationId}/messages` | 메시지·새 job 생성 |
| 비슷한 제품 | `GET /products/{productVersionId}/similar` | 조회만 |
| 찜·구매 전환 | `POST /me/wishlist`, `POST /me/products` | wishlist 또는 user product 생성 |

## 8. 수용 시나리오

1. **Given** 현재 목적과 공식 근거가 있지만 같은 역할의 보유품이 강하게 겹칠 때, **When** 의견을 요청하면, **Then** `OVERLAP`과 해당 보유품 근거를 반환한다.
2. **Given** 제품 버전은 확인됐지만 목적 관련 근거가 부족할 때, **When** 의견을 요청하면, **Then** `INSUFFICIENT`이며 없는 정보를 없다고 단정하지 않는다.
3. **Given** 추천 조사 후보 8개 중 3개만 게이트를 통과할 때, **When** 완료되면, **Then** 정확히 3개만 점수 순으로 반환한다.
4. **Given** 보유 제품이 검색 후보에 있을 때, **When** 추천하면, **Then** 최종 추천에서는 제외되고 비교 설명에는 참조할 수 있다.
5. **Given** 가격이 더 싼 후보, **When** 다른 판단 점수가 같지 않으면, **Then** 가격 때문에 순위가 올라가지 않는다.
6. **Given** 추가 질문에 사용자가 `잘 모르겠어요`라고 답함, **When** 쉬운 관찰 질문에도 답하지 않으면, **Then** 조건을 추정하지 않고 정보 부족을 표시한 0~5개 결과를 반환한다.
