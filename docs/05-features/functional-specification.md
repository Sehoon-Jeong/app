# SkinCause MVP 기능명세서

이 문서는 SkinCause MVP의 **사용자 기능 28개**를 한곳에서 확인하는 기능명세서다. 기능 하나는 GitHub Story 하나와 대응한다.

- `P0`: 핵심 실험 흐름을 성립시키는 필수 기능
- `P1`: 같은 MVP에서 완성도와 사용 편의를 높이는 기능
- 기능 ID는 바꾸지 않는다. 기능의 상세 결정이 달라지면 이 문서와 연결된 Story를 함께 수정한다.
- 화면 배치와 시각 표현은 디자인이, 요청·응답은 OpenAPI가, 저장 구조는 데이터 사전이 책임진다.

## 시작·계정

### FN-AUTH-01 이메일 회원가입·로그인

| 항목 | 명세 |
| --- | --- |
| 시작 조건 | 로그인하지 않은 사용자가 처음 가입하거나 기존 계정으로 돌아온다. |
| 입력·행동 | 이메일과 비밀번호로 가입 또는 로그인하고, 필요하면 로그아웃한다. |
| 시스템 처리 | 이메일을 정규화하고 비밀번호는 단방향 해시로 저장한다. 15분 access JWT와 7일 회전형 refresh session을 발급·검증한다. 로그인 후 서버에서 현재 안정 루틴과 열린 실험을 조회한다. |
| 사용자 결과 | 신규 사용자는 안정 루틴 등록으로, 기존 사용자는 진행 중인 실험 또는 홈으로 이동한다. 재접속해도 자신의 기록을 이어간다. |
| 핵심 규칙 | 데이터 소유자는 인증 정보로 결정한다. 프론트엔드가 보낸 사용자 ID를 신뢰하지 않는다. 인증 실패 응답과 로그에 비밀번호·JWT·계정 존재 여부를 노출하지 않는다. |
| 예외·복구 | 잘못된 형식과 자격 증명은 수정 가능한 오류로 안내한다. access JWT 만료 시 refresh session으로 한 번 연장하고, 둘 다 만료되면 기록을 유지한 채 재로그인을 요청한다. 소셜 로그인·비밀번호 재설정은 MVP 밖이다. |
| 완료 기준 | 가입 후 안정 루틴 등록에 도달한다. 기존 사용자의 루틴과 열린 실험이 복원된다. 로그아웃 후 개인 API 접근이 차단된다. 다른 사용자의 식별자로 기록을 조회할 수 없다. |
| 상세 원본 | [Story #45](https://github.com/sksksksksksss/service/issues/45) |

### FN-AUTH-02 계정과 기록 삭제

| 항목 | 명세 |
| --- | --- |
| 시작 조건 | 로그인한 사용자가 삭제 범위와 되돌릴 수 없다는 안내를 확인한다. |
| 입력·행동 | 비밀번호 재입력 또는 확인 문구로 삭제 의사를 확정한다. |
| 시스템 처리 | 새 쓰기를 잠그고 이미지·알림 구독·사용자 소유 데이터·개인 제품·인증 계정을 단계적으로 삭제한다. 현재 세션을 즉시 종료하고 실패 단계는 재시도 가능한 비민감 상태로 남긴다. |
| 사용자 결과 | 삭제 직후부터 기존 계정과 개인 기록에 접근할 수 없다. |
| 핵심 규칙 | 삭제 대상은 인증된 사용자의 소유 데이터로 한정한다. 공용 카탈로그는 보존하고 개인 제품 초안은 삭제한다. 백업은 공급자 보존 주기 안에서 최대 30일 후 제거될 수 있음을 사전에 알린다. |
| 예외·복구 | 확인 실패나 취소 시 아무것도 삭제하지 않는다. 외부 파일 삭제가 실패해도 계정을 재활성화하지 않고 해당 단계부터 재시도한다. 반복 요청은 한 번의 삭제 작업으로 처리한다. |
| 완료 기준 | 세션·개인 조회·새 쓰기가 즉시 차단된다. 루틴부터 LAB·파일·알림까지 삭제된다. 기존 JWT와 이메일로 과거 기록에 접근할 수 없고 다른 사용자의 데이터는 영향받지 않는다. |
| 상세 원본 | [Story #46](https://github.com/sksksksksksss/service/issues/46) |

## Lab Setup

### FN-RTN-01 안정 루틴 저장

| 항목 | 명세 |
| --- | --- |
| 시작 조건 | 로그인했고 계획·진행·보류 중인 실험이 없다. 카탈로그 제품 또는 확인한 개인 제품을 선택할 수 있다. |
| 입력·행동 | 피부 고민 또는 `잘 모르겠어요`, 아침·저녁 제품과 실제 사용 순서를 입력하고 현재 문제없이 쓴다는 사실을 직접 확인한다. |
| 시스템 처리 | 제품·시간대·순서 중복을 검증한다. 확인 전에는 초안으로 저장하고, 확인하면 이후 비교 기준이 되는 불변 루틴 버전을 만든다. |
| 사용자 결과 | 확정 시각과 아침·저녁 제품 구성을 확인하고 이후 추천·비교의 기준으로 사용한다. |
| 핵심 규칙 | 전체 루틴에는 제품이 하나 이상 있어야 한다. 같은 제품은 아침과 저녁에 각각 둘 수 있지만 같은 시간대에 중복할 수 없다. AI가 안정 여부를 판정하지 않는다. 열린 실험이 참조하는 루틴은 종료 전 바꿀 수 없다. |
| 예외·복구 | 제품을 찾지 못하면 직접 등록으로 이동한다. 안정 확인이 없으면 추천 기준으로 쓰지 않는다. 저장 실패 뒤에도 작성 중 입력을 유지한다. |
| 완료 기준 | 루틴을 저장·재조회한다. 확인 없는 입력은 안정 루틴이 되지 않는다. 중복과 잘못된 순서를 거부한다. 편집해도 과거 버전과 실험 참조가 보존된다. |
| 상세 원본 | [Story #7](https://github.com/sksksksksksss/service/issues/7) |

## 제품 선택

### FN-REC-01 개인화 제품 추천

| 항목 | 명세 |
| --- | --- |
| 시작 조건 | 확인한 안정 루틴이 있다. 사용 목적과 추가·교체 의도를 정했고, 교체라면 대상 제품을 골랐다. |
| 입력·행동 | 피부 고민, 사용 목적, 추가·교체 의도와 선택 조건을 입력한다. 모르는 항목은 `잘 모르겠어요`로 남길 수 있다. |
| 시스템 처리 | 서버가 카탈로그에서 추천 자격이 있는 실제 제품을 정하고 목적 관련성·개인 이력·루틴 변화·정보 확인 수준을 계산한다. AI는 허용된 제품 안에서 순위와 설명을 제안하며 서버 검증 실패 시 규칙 기반 순서를 사용한다. |
| 사용자 결과 | 실제 제품 후보를 최대 3개까지 보고 목적 관련성, 현재 루틴과의 관계, 주요 중복과 관찰 이유를 확인한다. |
| 핵심 규칙 | 추천은 구매 답안이나 피부 적합성 보장이 아니라 다음 실험 후보다. 운영 확인된 제품만 사용한다. 관련 개인 기록은 일반 정보보다 먼저 반영하되 불편 이력을 숨기지 않는다. 후보가 적으면 수를 억지로 채우지 않는다. |
| 예외·복구 | 안정 루틴·교체 대상·적격 후보가 없으면 이유와 필요한 다음 행동을 안내한다. 정보가 부족해도 추측하지 않고 부족 상태를 표시한다. 진단·치료 조언·적합성 단정을 하지 않는다. |
| 완료 기준 | 루틴이 다르면 추천 이유도 달라진다. 모든 카드에 실제 제품과 관찰 이유가 보인다. 개인 실험이 다음 추천에 반영된다. AI 실패에도 검증된 규칙 기반 후보를 제공한다. |
| 상세 원본 | [Story #8](https://github.com/sksksksksksss/service/issues/8) |

### FN-CAN-01 실험 후보 저장

| 항목 | 명세 |
| --- | --- |
| 시작 조건 | 안정 루틴이 확정됐고 추천 카드 또는 검색 결과에서 제품을 선택했다. 목적과 추가·교체 의도가 있다. |
| 입력·행동 | 제품을 `실험 후보로 저장`하고 목적·변경 방식·교체 대상을 확인한다. |

## 기능명세와 구현 계약의 관계

- 기능의 목적·조건·처리·결과·규칙·예외·완료 기준은 이 문서와 연결된 Story가 책임진다.
- endpoint, 요청·응답 필드와 오류 코드는 [OpenAPI](../api/README.md)가 책임진다.
- 엔터티, 소유권, 상태와 제약은 [데이터 사전](../06-data-model/data-dictionary.md)이 책임진다.
- 실제 분배와 구현 확인은 Story 아래의 GitHub Sub-task에서 관리한다.
- 서로 충돌하면 제품 의미는 Story와 이 문서를 함께 고치고, 기술 계약은 같은 변경에서 동기화한다.
